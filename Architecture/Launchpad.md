# Launchpad

`Sources/Modules/Launchpad/` is an app launcher: what is installed, how the person arranged it, what they hid. The engine (`Engine/`) reads, edits and launches; the UI (`UI/`) is a full-screen window the person opens with a shortcut they record, and a settings page, registered in `Sources/HelmApp/ModuleRegistry.swift` (`LaunchpadDescriptor`). The reasons live on the doc comments of the code that carries them:

- an app is its bundle id and nothing else is stored; a path belongs to the latest catalog read, so a planted layout file cannot make Helm launch a path: `Sources/Modules/Launchpad/Engine/Logic/LaunchpadLayout.swift`;
- the three roots, the walk judged by name and one `lstat`, the duplicate rule (earlier root, then smallest path), and why Safari is no fourth root: `SystemPorts.swift` (`FileSystemAppCatalog`);
- a read that was not `complete` drops nothing, and a read never writes: `Sources/Modules/Launchpad/Engine/Logic/LaunchpadReconcile.swift`, `LaunchpadEngine.swift`;
- every file read out of a bundle (`Info.plist`, `InfoPlist.strings` of the lproj `Bundle.preferredLocalizations` picks) goes through one reader that opens without blocking, follows no link at the last component, takes a regular file only and stops at `LaunchpadLimits.maxFileBytes`, so a pipe or a huge file planted in a bundle cannot hold the walk: `SystemPorts.swift` (`cappedRead`);
- a tile says its name in `.help`; a name with no space or hyphen to break at (German "Festplattendienstprogramm", 145.3 pt at 11 pt) takes one line and shrinks to `LaunchpadMetrics.unbreakableShrink` (0.78; `minimumScaleFactor`, `allowsTightening`) rather than split mid-word; the cell is square now, so the room is the icon plus the chrome less the side padding, and the bare word shrunk (116.7 pt at 11 pt, measured by `LaunchpadLabel.overflow`) is whole from 1440 x 900 at x1 up and cut at 1024 x 768 and 1280 x 800 (room 97.1 and 110.6 pt at x1; printed by `testTheMarqueeCanReachTheWholeGermanNameOnTheScreensListed`). A place to break is a space, a hyphen, a soft hyphen (U+00AD: the built German and Portuguese names carry them; the German was read from Disk Utility's built `InfoPlist.loctable` (de) with `plutil -convert xml1` on this machine, 2026-11-22; "Festplatten\u{AD}dienstprogramm", and break there, tried with a hosting view in `LaunchpadLabelTests`) or a Han, Hiragana, Katakana or Hangul letter (`LaunchpadLabel.canBreak`): such a name takes two lines at 0.85 and the built disk-utility name is whole on every screen listed. A cut name scrolls under the pointer (§ A cut name scrolls on hover), and `.help` names it whole. Automatic is seven columns on every screen, and a manual grid of up to 10 columns goes under the room a name needs, where `.help` carries it: `Sources/Modules/Launchpad/UI/LaunchpadTiles.swift`, `Sources/Modules/Launchpad/UI/LaunchpadGeometry.swift`;
- the window measures nothing: its sizes come from the screen's size and the grid settings (once, and again only when those change: `regrid`), its pages are placed by offset, three at most exist as views, its icons are its own cache and go with it, and pass 3's page, in whose run the log showed the system switching the keyboard tap off and memory up 559 MB, is why: `LaunchpadGeometry.swift`, `LaunchpadScreen.swift`, `LaunchpadIcons.swift`, and `TheLaunchpadWindowMeasuresNothingTests`, an optional test run on request (`bash Scripts/test.sh --filter TheLaunchpadWindowMeasuresNothingTests`);
- the window's level is one below the Dock's, so the Dock stays drawn and clickable over it and the menu bar draws over its top strip (§ The Dock icon): `Sources/Modules/Launchpad/UI/LaunchpadWindow.swift`;
- where each tile of a page sits is one pure function: a small tile is a cell, a large folder a block of 2×2, first fit in reading order, so a small tile fills the strip a block skipped; drawing, paging, the pointer's hit test, the lift's gap and the arrow keys all take their cells from it, and a page ends at the first tile that does not fit: `Sources/Modules/Launchpad/UI/LaunchpadPlacement.swift`;
- the pinch reads a private framework through one port, trusts no frame it hands over and stands down when its layout is not the assumed one; Helm only reads the system's own pinch setting: § The trackpad pinch;
- the launch counts are a second private file beside the layout, bounded by the same ceilings, never read to judge a launch, and the category view's order is one pure rule over them and the catalog's date added: § The category view, `Sources/Modules/Launchpad/Engine/LaunchCountStore.swift`, `Sources/Modules/Launchpad/Engine/Logic/LaunchCounts.swift`, `Sources/Modules/Launchpad/Engine/Logic/LaunchpadCategories.swift`;
- the layout file is private, bounded, and a bad one is moved aside once before the first save: `LayoutStore.swift`, `Sources/Modules/Launchpad/Engine/Logic/LayoutCoding.swift`, `Sources/Modules/Launchpad/Engine/Logic/LaunchpadLimits.swift`.

## The catalog and the layout

`AppCatalogPort.read()` is pull-only; a change in the installed set is seen on the next read, and `observeChanges` tells the model when to ask (`CatalogChange.concerns` in `Sources/Modules/Launchpad/Engine/Logic/CatalogChange.swift` keeps a path that ends at an `.app` or at the `Info.plist` inside its `Contents`, and a path with no `.app` component unless its last component is hidden). An absent or empty root reads as empty and complete; a root that exists but will not open, or a walk stopped at the ceiling on apps, makes `CatalogReading.complete` false. The layout is saved only on a person's edit (`LaunchpadEngine.apply`), through one lock over read, reconcile, edit and save; only the latest catalog read is kept (an edit reconciles against it; the layout is read afresh each time) and the calls block on disk, so a model hops with `offTheCooperativePool`.

**Drops are edits by anchor.** An edit names where an item goes by the id of the item beside it, never by an index, because the window draws a subset of `layout.items` (`LaunchpadEdit`, `LaunchpadLayout.edit(dropping:source:destination:folderName:)` in `Sources/Modules/Launchpad/Engine/Logic/LaunchpadLayout.swift`; a folder never nests; a drop that changes nothing is nil). **A page break is an item**, `.pageBreak`, stored as `{"pageBreak": true}` in the same list (`LayoutCoding.swift`): it stays where it is when its neighbour is moved away, `normalized()` keeps one only between two items and at most `LaunchpadLimits.maxPages - 1` (199) of them, the later dropped, the file's version stays 1 and a file without breaks reads as it did. A catalog app carries its raw `LSApplicationCategoryType` (`CatalogApp.category`). **Folder names** are Helm's own words, copied from two tables of macOS and never read from them at run time (private files in a layout nobody promised): the iPhone's own folder-naming table, `FolderNaming.loctable` in `/System/Library/PrivateFrameworks/FrontBoard.framework/Versions/A/Resources` (`plutil -convert json -o - <it>`; tables `en`, `de`, `es`, `fr`, `ja`, `pt_BR`, `ru`, `zh_CN`), wherever it has the category; and for the six it lacks (Developer Tools, Graphics & Design, Video, Food & Drink, Magazines & Newspapers, Shopping) the descriptions of the `public.app-category.*` types in `/System/Library/CoreServices/CoreTypes.bundle/Contents/Resources/InfoPlist.loctable` (keys such as `Graphics n Design`). `LaunchpadCategoryName.swift` maps the 28 `public.app-category.*` ids that table lists, bar the games subtypes, to catalog words (`categoryBusiness` … `categoryWeather`; every `*-games` subtype is Games; the target's category, else the dropped app's, else `categoryOther`, "Others", which is plural and is Helm's own: Autopilot's "Other" is one file kind). Utilities and Video are the kit's words (`HelmWord.utilities`, `HelmWord.video`) since the host and Autopilot draw them too (§ Words two parts draw in `Architecture/Localization.md`). One exception to the first source: English "Health" is Homebrew's, so Healthcare & Fitness keeps CoreTypes' English (`OneEntryPerKeyTests`).

**A folder's size is the folder's.** `Folder.large` is one flag, stored as `"large": true` inside the folder's own entry and written only when set, so a small folder's file is as it was and the version stays 1 (an older build ignores the key and drops it at its next save, as it does a page break). Anything under that key but `true` (a string, a number, null, a list) reads as small and the folder reads normally; an app or a page break carries no such key and a hand-edited one is ignored (`LayoutCoding.swift`). The edit is `.resize(folder, large:)`, refused when the folder is not there or already has that size, so a stale menu writes nothing; every edit that keeps the folder keeps the flag, and a folder reduced to one app dissolves with it. **Reset arrangement** builds new folders, so every folder is small again (`ALargeFolderSizeIsWrittenOnlyOnAFolderAndNeverLostTests`).

**A moved app.** `LaunchpadLayout.categoryOverrides` (beside `hidden`) holds the apps the person sent to another category in the category view, stored as `"moved": {"<bundle id>": "<category slug or others>"}` and written only when there is one, so a file without moves is byte-identical to before and the version stays 1 (an older build ignores the key and drops it at its next save, as it does `large`). The value is a `LaunchpadCategoryTarget` (a category, or Others), not a block's `Kind`, which also has Recently Added, never a place to send an app. `LayoutCoding.swift` reads it leniently: anything but an object under `moved` reads as no moves, an entry whose value is not a known slug or whose key is empty is skipped and the rest of the file reads, a key is cut at the id ceiling and at most `LaunchpadLimits.maxApps` entries are read, by sorted id; `normalized()` bounds it again and **carries it, which is the whole reason Reset arrangement keeps it** (a move is not an arrangement of the grid; `AMoveToACategoryIsWrittenOnlyForAnInstalledAppAndAKnownCategoryAndNeverLostTests` pins it). The edits are `.setCategory(app, target)` (nil gives the app back to its own category) and `.returnAllToOwnCategory`; each is refused when it changes nothing. The layout holds no categories, so the engine's `resolved` (`Sources/Modules/Launchpad/Engine/LaunchpadEngine.swift`) refuses an app the last read does not find and turns a move to the category the app already has into "take the move away", so nothing is stored for it. `reconciled` drops the move of an app a **complete** read does not find (like `hidden`) and never on an incomplete one. `read()` reconciles in memory and writes nothing, so the move leaves the snapshot at once and the file only at the next save; an app uninstalled and reinstalled with no edit between gets its move back, as `hidden` does; a hand-edited move equal to the app's own is left, harmless in grouping, and counted in "Moved apps". `ABadMoveEntryInTheLayoutFileIsIgnoredNotFatalTests` pins the reading.

**The date added.** `CatalogApp.added` is the date Finder shows as "Date Added" for the bundle (`ATTR_CMN_ADDEDTIME`), because a copy keeps the creation date and a freshly dragged-in old build would not read as new; Spotlight's date needs Spotlight on and the folder indexed. It is nil, and the app is never "recent", for an app in `/System/Applications` (a macOS update adds them all again), for a symlinked bundle (Safari in `/Applications`: the date would be the link's) and for a value that would not read. A nil is not logged per app; the read's one log line counts the apps "without a date added". The read is one `getattrlist` per app after the walk's `lstat`, not `URLResourceValues`: the resource-values call made about 350 bytes more per app over 1500 bundles (1992 against 1642 bytes an app), measured by the optional `TheDateAddedIsReadOncePerAppAndCostsTheWalkNothingTests`, and `getattrlist` makes no Foundation objects. An app updated in place (Sparkle, the App Store) is added to its folder again and shows as recent for 30 days; a ledger of first sightings would avoid that and cannot work on a first run.

A hidden app leaves its folder. The module is not a `BackgroundScanning` module: it is read on demand with the person present, and has no report. The layout is not a sealed setting: it reorders, hides, moves apps to another category and names no path.

## The default arrangement

What a person sees with no arrangement of their own: `LaunchpadLayout.defaultArrangement(for:utilitiesFolderName:)` in `Sources/Modules/Launchpad/Engine/Logic/LaunchpadDefaultArrangement.swift`. Apple's apps stand in the Dock's order, then one folder of the system utilities, then a page break, then every other app in catalog (A–Z) order. It is used in two places only, both in `LaunchpadEngine`: a read or an edit with **no layout file** (`LayoutRead.absent`; the first edit saves what the person was shown, hidden apps aside), and `.resetArrangement`, which keeps `hidden` and the moves to other categories and takes the default's items. A stored layout is never rearranged by it, and an unreadable file still shows the catalog's order, as its warning says. New apps installed later go to the end, as `reconciled` always puts them.

Apps are told by bundle id, never by name; an id on the list that is not installed is skipped, and an app on no list falls into the A–Z block. The two lists are literals copied at build time and never read at run time: the Apple order from `persistent-apps` of the Dock's own default property list, in `/System/Library/CoreServices/Dock.app/Contents/Resources` (`plutil -p`; Keynote, Numbers and Pages are the `/Applications` ones), then the `/System/Applications` apps the Dock leaves out in the old Launchpad's order, `Apps` last; the utilities from the `CFBundleIdentifier` of every app in `/System/Applications/Utilities` plus Automator, Font Book, Image Capture and Time Machine. A utility is also any app whose path lies under `/System/Applications/Utilities/`, so one a later macOS adds lands in the folder. A folder of fewer than two members dissolves (`normalized()`). The folder has one fixed literal id, so an open folder survives the default being built again on each read. The folder's name is the kit word `HelmWord.utilities`, passed in as a closure by the descriptor (`LaunchpadEngine.init(utilitiesFolderName:)`), asked each time a default is built, so a language change shows; the engine holds no strings.

## How Launchpad's model reaches its engine

`LaunchpadViewModel` (`Sources/Modules/Launchpad/UI/LaunchpadViewModel.swift`) is built with the engine by the descriptor's `makeModule` and held by the host. It reaches the engine only through its `LaunchpadWork` port, which `LaunchpadEngine` conforms to: `read`, `hide`, `unhide`, `resetArrangement`, `launch`, `observeChanges`; a drop, a rename, a resize, a move to a category (`.setCategory`) and "Return all" (`.returnAllToOwnCategory`) are `LaunchpadEdit`s through `apply`. Every blocking call hops off the main actor with `offTheCooperativePool`, and its answer is dropped when a newer request exists or the model was stopped: a snapshot by a newer read, a notice by a newer edit or launch (`LaunchpadViewModel.acts`). A launch's notice names the app on the tile that was pressed, taken before the launch.

A launch is resolved in the engine, not the model: `launch(id)` reads the catalog afresh, finds the id, asks the bundle at that fresh path for its id and only then hands the URL to `AppLauncherPort` (`Sources/Modules/Launchpad/Engine/Logic/LaunchResolution.swift`). A path never comes from the layout file or from the page's last snapshot. The answer is a `LaunchOutcome` (launched, gone, unreadable, failed); the model turns the last three into a notice. `SystemAppLauncher` (`Sources/Modules/Launchpad/Engine/SystemPorts.swift`) is the only code that opens an app, and in a test process it answers false and calls nothing (`TheSuiteDoesNotLaunchAppsTests`). **The count is recorded after a successful open**: in `LaunchpadEngine.launch`, only when `AppLauncherPort.open` answers true, once, through `offTheCooperativePool` (a disk write); a gone, unreadable or failed launch counts nothing, and the model and the window record nothing. `LaunchpadWork` also has `resetLaunchCounts`, which does nothing when there is no file and otherwise writes the empty document and removes the `.unreadable` aside (it holds bundle ids and counts); a failed write answers nil and the model reads again. The model's `makeAuth` (default `SystemLaunchpadAuth`) gives each Hidden-block gate, the window's and the settings page's, a port of its own, so a test can put a fake in.

The model starts nothing in `init`. The settings page's `.task` and the window each call `whileShown()`, which subscribes to the catalog watch before its first read, so no change falls between the two; the token it gets is local to that task, so leaving cancels the task and stops the watch. Each caller is a watcher of its own: the snapshot and the notice are dropped when the last one leaves, and an answer that lands while nobody watches is refused, so a closed window holds no list of apps. Events are buffered to one, so a burst is one more read. On the person's switch and on quit the host calls the descriptor's `stop(_:)`, after which the model reaches no work. **Who reads, and why.** Every catalog read says what asked on its log line (`read N apps (open)`; `CatalogReadReason`: `open` the window's first read, `watch` a change in the watched folders, `launch`, `refresh` a refused edit, `settings` the page's first read, `reset`, `edit`). A watcher that joins another (the settings page while the window is open) reads nothing at its start and, of the watchers, only the oldest reads for a change (`LaunchpadViewModel.whileShown`), so two watchers are one read; the later one keeps the snapshot if the earlier leaves. A launch that opened the app refreshes only when a watcher other than the window's own is there (told by watcher id, `windowWatchers`, not by a held window handle, which exists before its watch runs) (the settings page's Reset reads the new counts): the window closes with the launch and drops the snapshot, and the launch's own fresh read stays (`LaunchpadEngine.launch`). `resetLaunchCounts` reconciles against `lastCatalog`, as every edit does, and reads only when nothing was read before. `TheCatalogIsReadOnlyForWhatNobodyHasAlreadyReadTests` counts them.

## The window

The model is the one door: `showLaunchpad()` and `toggleLaunchpad()` (the shortcut's press) open the window or bring the open one forward, `closeLaunchpad()` and `stop()` close it; `present`, set by the descriptor, builds it, and a model without it (a test) opens nothing (`LaunchpadWindowHandle` is the seam). The shortcut is the descriptor's `LaunchpadHotkey` slot, with no default: it holds nothing until the person records one, and the host registers it only while the module is live.

`LaunchpadWindow` (`Sources/Modules/Launchpad/UI/LaunchpadWindow.swift`) is a borderless non-activating panel over the screen the pointer is on, not a `HostWindow`: Helm stays an accessory, with no Dock icon and no Space pulled. It is built when asked for, with its own `LaunchpadScreenState` (geometry, search, page, the arrow keys' choice, the open folder) and its own icons, runs the model's `whileShown()` while open, and releases all of it when it closes. It closes on Esc (an open folder first, then the search), a click on the empty background, an app that opened (a failed launch leaves it open with the notice), the panel losing key and another app coming forward (neither while the Hidden prompt is up), the Space or the screens changing, the model stopping and the shortcut's second press. Opening and closing write `module.launchpad.*` memory lines, each only when it can (`module.launchpad.show` when the first snapshot lands before the window closes, `module.launchpad.close` when both its readings could be taken: the before at the start of `finish()`, the after on the next main-queue turn, while only the show line uses the footprint from the window's making; see the readings paragraph below). **How much of it shows has one writer**, `LaunchpadWindow.apply`: the panel's alpha and `state.reveal` (`LaunchpadReveal`, its own object so a scrub republishes only `RevealEffect`, which draws the content's zoom from `LaunchpadMetrics.zoomFrom` to its size and its opacity; no `.animation`). The number is the fingers' progress during a scrub and a settle's own clock after it: `settle` reads the display link of the panel's content view (`LaunchpadSettleLink`, `DisplayFoldLink`'s pattern) and moves from where the reveal is to its target along `HelmMotion.interfaceProgress(at:)`, fixed durations (`windowZoomDuration` in, `interfaceDuration` out and back); a timer a little past the end lands the same settle if the link never ticked. It opens by a settle to 1; it closes by the model forgetting it at once and a settle to 0 from where it is, with the keys swallowed (`isClosing`) and the mouse ignored (`ignoresMouseEvents`, so a click goes through to what is behind); then `finish()` takes the panel down; a window opened over a fading one cuts it first (`lingering`). Reduce Motion cuts both and turns the zoom, the icon's pop and the glow off. A folder's card grows from its tile's slot (`LaunchpadGeometry.center(of:)` of the tile's `LaunchpadPlacement.Slot`, computed, not measured) and folds back to it; the selected tile's wash (the arrow keys' choice, and the first search hit) carries a Metal glow (`LaunchpadGlow.metal`, compiled by SwiftPM into the target bundle's `default.metallib`, which the build needs the Xcode MetalToolchain component for; a failed compile is one log line and the plain wash). Tiles sit in left-aligned slots, so a short last row keeps its columns. **Lifetime and readings.** What SwiftUI's hover and context-menu responders keep after the window is gone (a leak the owner's `leaks` run showed: the state, its icon cache and about a hundred icons kept on every open) must not be able to reach the window's state: every closure the screen gives a tile (`open`, `hide`, `move`, `resize`, the category menu's) holds `state` weakly (`LaunchpadScreen`), and `finish()` empties the icon cache (`LaunchpadIcons.removeAll`) once the picture is down; `AClosedLaunchpadWindowLeavesNothingOfItselfBehindTests` opens and closes the real window three times with its tiles' menus asked for and holds weak references to the state, its icons and the window. The open is a registry phase, `launchpad.open`, from the window's making to the first state update that holds a snapshot (`watchOpening`), and the `module.launchpad.show` reading is taken there, with a line `window: first snapshot landed N ms after it was made` (the snapshot's arrival in the state; no frame is awaited); `module.launchpad.close` is read after the run-loop turn that follows `finish()`, so the reading is meant to count what the views let go (the intent; not measured). A window that closes before its snapshot lands ends the phase and writes no show line and no `landed` line; its close line is still written when a footprint could be read.

What is drawn follows `snapshot` and the search: busy (no answer yet), empty (no app), no match, or the pages, with a notice banner above the dots. Pages are an offset and a number. A trackpad swipe with fingers on it drags the page and settles it on release: `LaunchpadSwipe` (pure) turns each event into a drag or a release, the offset is a rubber band past the first and last page, a release turns by half a page or by a flick (300 pt/s from 40 pt), and a touch that begins while the last release settles is ignored; the 120 Hz of the drag publishes only `LaunchpadPageDrag.offset`, read by `PageDragOffset` alone, never the state; `settle` changes the page and zeroes the offset in one `withAnimation(HelmMotion.pageSettle(velocity:distance:))`. The wheel and a device with no phases turn one page (`LaunchpadScrollPager`), as do the arrows, the dots and the arrows' choice, all on `interface`; typing sends the page to the first at once and the tiles slide to their new slots, and the first snapshot is not animated. The arrows move a choice that Return opens (Left and Right stay the search field's while it holds text): an app launches, a folder opens a card over the dimmed page; hiding is the tile's context menu. **An open folder's card has pages of its own**: `(columns - 1) × (rows - 1)` apps to a page (`LaunchpadSurface.Card.capacity`, `pageCount`; the card is as wide as `min(count, columns - 1)` cells) and no scrolling. The swipe, the wheel, the arrows and a row of dots drawn in the card under the tiles (only when it has more than one page; the card grows one `cardDots` row for them) turn its pages as they turn the grid's, through the same routes: `state.cardPage` and `state.cardDrag` (its own `LaunchpadPageDrag`, read by `PageDragOffset` on the card's tiles), a second `LaunchpadSwipe` in the panel (`cardSwipe`, so the two gestures never share their travel), and `state.swipeWidth` (the card's page width, or the grid's) for the half-page rule; `drag`, `settle`, `turn` and `go` branch on `openFolder`. The arrows move the choice in the folder's flat order and the page follows it (`goCard(to: card.page(ofIndex:))`); the first press after a turn chooses the shown page's first app. A card's tiles are addressed by their index in the folder's whole list, never by place on a page: `LaunchpadHit` adds `page * capacity`. `cardPage` is 0 when a card opens by a click, Return or a new folder, and the last page when a lift opens it (the gap is at the end); a new grid (`regrid`) keeps it on the choice or on the tile the page began with, and a snapshot that shortens the folder clamps it. A drag held when a folder opens or a search is typed is let go there, since no release will come (a swipe in progress when a card opens or closes is handed to the other instance of the gesture, and not carried over). Under Reduce Motion a release settles at once and locks nothing. The switch between Apps and Categories is the kit's `HelmHeaderTabs` (public since pass 14: another target uses it) on the search row at the side margin, drawn only when `LaunchpadGeometry.switchFits` says the window leaves it `LaunchpadMetrics.switchRoom` (216 pt: the widest strip, Russian at 196 pt measured by `fittingSize`, plus a 20 pt gap); it is dimmed and disabled while the search holds text. § The category view.

**Large folders.** The folder tile's context menu (and VoiceOver's actions) offers the other size, "Enlarge folder" or "Shrink folder" (`LpStr.enlargeFolder`, `shrinkFolder`), written through `LaunchpadViewModel.resize`; the tiles around it move with `HelmMotion.reorder` (`animateNextUpdate`, armed by a resize that asks for a size the shown folder lacks, and by a move in the category view that changes the app's category (**Move to category** below), and spent by the next update, answer or not; instant under Reduce Motion). **A page holds `capacity` cells, not `capacity` tiles**: `LaunchpadPaging.pages` cuts the list at each page break and then by what `LaunchpadPlacement.place` fits, so a page of large folders holds fewer tiles, a page is still a run of the stored order, and a page's first tile always fits. A block goes to the first place in reading order where 2×2 is free and the small tiles flow around it, so a small tile can be drawn before an earlier-stored block; the stored order is not changed. A grid under two cells a side (not reachable from `LaunchpadGeometry.counts`: columns 3 or more, rows 2 or more) draws every folder small. A large folder shows its first nine apps as large icons, three by three (`LaunchpadGeometry.largeMark`: the block's height less what a tile holds besides its icon, which the square cell makes its width too); with more than nine, the ninth cell shows four tiny icons of apps 9 to 12, two by two, and a click on it opens the folder. The inner icons are plain images, not buttons: the panel takes the press before a button sees it, so `LaunchpadScreenState` resolves a click from the press's point (`LaunchpadHit.icon(at:block:mark:edge:iconTop:apps:)`, from the same `LaunchpadFolderMark.frame(ofIcon:size:edge:)` the mark is drawn by); a one-cell folder's well is 0.85 of the mark's frame, centred (`LaunchpadMetrics.wellShare`), a large mark's well (a large folder's, a category's, the Hidden block's) is the mark less twice a small icon's inset (`LaunchpadGeometry.largeEdge`, § The grid scales to the screen), and the corner is 0.225 of the well's side (`wellCorner`), as an app icon's body is, and every frame the clicks read is inside it: an icon launches that app, anywhere else on the block, the gaps between icons included, opens the folder. The press records which icon it is on (`pressedIcon`, the app's id): that icon takes the press wash (the block washes only when the release will open the folder) and, once launched, the swell the app tiles have (`popped`, off under Reduce Motion); a block that moved since the press launches only if the same app is under the press's point at the release, else it opens its folder and launches nothing. VoiceOver sees one element for the block. A search is flat and shows apps only, so a large folder is not in its results and the search shows small apps. The arrow keys keep the stored order left and right (a block is one stop); on a page with a large folder Up and Down follow the cells (the tile covering the cell above or below, in the tile's left column, else the choice stays; `LaunchpadPlacement.vertical`), and a page with none keeps the index arithmetic.

**The system's dialog.** While the Hidden block's prompt is up (`LaunchpadWindow.promptChanged`, called by the gate's `onAsking` before the ask starts), the panel's resign-key and another app's activation (`LaunchpadWindowEnders`' `ignoringActivation`) end nothing, the panel takes no mouse and its keys are swallowed (`LaunchpadPanel.isPrompting`), and when the prompt ends the panel takes the key back as `present` does. Space and screen changes still close the window (sleep closes only a scrub, § The trackpad pinch).

### The icons

The window never draws an icon on main. `LaunchpadIcons` (`Sources/Modules/Launchpad/UI/LaunchpadIcons.swift`, the window state's own, `@MainActor`) answers `image(for:side:)` and nothing else to the views: a hit is a one-representation `NSImage` at that side, a miss asks a private `OperationQueue` (at most four at once, `.userInitiated`; not `offTheCooperativePool`, which has no bound) to draw it with `LaunchpadIconRender` (`NSWorkspace.icon(forFile:)` drawn once into a bitmap of exactly the pixels, Display P3, an `autoreleasepool` inside each call) and answers meanwhile the largest image that path has had at any size (any arrival fills it: a folder's mini, a quadrant, a tiny one, so an open folder's card shows the mini already on the page scaled), which the view scales, or nothing, which the view draws as an empty slot of the same frame (`LaunchpadIcons.empty`). The reason is the old cache: it kept the system's one multi-representation image per path (32 representations for Safari, Calendar and Finder on macOS 27.3, from `NSWorkspace.shared.icon(forFile:).representations.count`) and every distinct size a view asked for (the tile `g.icon`, a category quadrant, a folder's `mini`, a cluster's `tiny`) made the system render and keep one more bitmap inside it, on main, in the middle of a body. Each caller passes its own side, and the shared formulas are static (`LaunchpadCategoryMark.quadrant`, `LaunchpadFolderMark.mini`, `LaunchpadClusterCell.tiny`) so the view and the caller cannot disagree.

- **Once per (path, pixels).** The key is `"\(pixels)|\(path)"`, `pixels = side * scale` rounded; a pending set stops a second ask for a key in flight. The cache is bound by `LaunchpadIcons.limits`: a page asks at most nine keys per cell (a folder's minis), three pages are live and an open card's three ask one per cell, so `30 * capacity` images, and a cell is at most one tile's bitmap, so `6 * capacity * pixels² * 4` bytes; at 8 x 5, icon 80, 2x that is 1200 images and 24 576 000 bytes (23.4 MiB). Automatic is 7 x 5 and its icon is at most 160 pt (`LaunchpadMetrics.automaticIconCeiling` = 80 * 1.6 * 1.25; Manual keeps `iconRange`'s 128), so the largest Automatic grid, a 2x screen with the multiplier at 1.25 whose height holds the icon at 160 pt (a 16:9 screen from about 2986 x 1680; 2880 x 1620 holds 158), asks 35 cells at 320 px: 6 * 35 * 320² * 4 = 86 016 000 bytes, 82.0 MiB, the largest at 7 x 5 (2560 x 1440 holds 139 pt at x1.25, 278 px). Manual's largest is 10 x 8 at 128 pt, 256 px: 6 * 80 * 256² * 4 = 125 829 120 bytes, 120 MiB. The bound is soft where it must be: an arrival evicts only an entry not asked since the last `onArrival` was said (an `NSCache` evicted what the same redraw had asked, and a page of full folders drew and evicted for ever: `testAPageOfFullFoldersSettlesAndStopsDrawing`). A drawing that answers nothing is remembered as failed until the next `invalidate` and its slot stays empty; a `warm` waiting on it ends for that key. Arrivals say `onArrival` once per run-loop turn, whatever number landed; the state's closure is `[weak self]` and sends `objectWillChange`, so a queue operation, a pending ask or the closure keeps no state alive (the operations hold the cache weakly too).
- **A result may not outlive its asker.** `generation` is bumped by `removeAll` (the window is down; also empties `latest`, the waits and `onArrival`) and by `reconfigure` (a new grid or scale); an operation checks the generation before and after drawing (through an unfair lock, from its own thread), and the arrival block on main reads `generation` again and drops what is stale (twice: on the queue's thread after drawing, and again on main) (the payload is captured before the hop, the reading is taken inside it). A scale change also empties the cache: an image's point size is its pixels over the scale it was made for. `NSWindow.didChangeBackingPropertiesNotification` also fires with the scale unchanged (a colour space, the first ordering on screen), so `rescale` does nothing then and what is under way lands; after any `reconfigure`'s hold ends the cache says `onArrival`, so the slots asked before the change and dropped by it are asked again without an outside redraw.
- **A grid setting dragged** (`regrid` -> `reconfigure`) holds new asks for about 80 ms after the last change and drops those it had not started, so the side the drag stopped on is drawn and not each one it passed; what is drawn shows scaled meanwhile.
- **The first snapshot waits for page 0's icons** (`LaunchpadScreenState.update(snapshot:)`, only for a state made with the window's icons): page 0 as `LaunchpadPaging.pages` cuts it over the arrangement's segments (`layoutSegments`, the cut `reflow` makes: a page break ends it, an app the snapshot lacks takes no cell, a large folder takes four), in the apps view with no search, is drawn: apps at `geometry.icon`, a folder's apps at its `mini` (a large folder's last four at the tiny side; `LaunchpadFolderMark.cells`, shared with the screen), and the snapshot lands when they have or after `firstIconsDeadline` (120 ms), whichever is first; the mode stays `.busy` meanwhile. A race, not a wait: a late icon shows empty and arrives by `onArrival`. Closing cancels it (`shutdown`). A state made without icons (a test) lands at once. `LaunchpadWindow` logs `window: first icons drawn N ms after the snapshot arrived (M rendered, P px)`, timed from the snapshot's arrival through the wait (not from when it was applied), with `, timed out` only when the deadline ended the wait (`warm` says so; a drawing that failed does not), no path and no name; the line is silent when there is nothing to draw (page 0 asks no icon, or the view is not the apps view or a search is typed) and for every later snapshot; and reads the chosen screen's backing scale at its making and again on `NSWindow.didChangeBackingPropertiesNotification` (`LaunchpadScreenState.rescale`).

The settings page keeps `AppInfo.icon(forFile:)`: it is a page of a window that stays, not a grid that opens and closes. Tests, all optional (`Tests/optional-tests.txt`; `bash Scripts/test.sh --filter 'TheLaunchpadIconPipelineUntriedInputsTests|TheLaunchpadIconsAreAskedForAgainWhenTheScreenChangesTests|TheLaunchpadIconsAreRenderedOnceAtTheirSizeTests|TheLaunchpadIconCacheReturnsUnderItsBoundTests'`): `TheLaunchpadIconPipelineUntriedInputsTests` (a side that is no side, a drawing that answers nothing, a page of full folders that must settle, the fallback from any side, the gate's set, a close in the middle), `TheLaunchpadIconsAreAskedForAgainWhenTheScreenChangesTests` (a rescale to the same scale keeps what is under way; to a new scale ends with every asked slot filled and no outside redraw), `TheLaunchpadIconCacheReturnsUnderItsBoundTests` (the cache's bound and what it returns under it), `TheLaunchpadIconsAreRenderedOnceAtTheirSizeTests` (one drawing per path and side however many ask; one representation at the point size; four sides four drawings; a drawing under way at `removeAll` lands nowhere; a new scale draws again; the first snapshot's gate and its deadline; the system's own drawing off main), `AClosedLaunchpadWindowLeavesNothingOfItselfBehindTests`.

### Show in Finder, Copy Path and the new dot

**Show in Finder and Copy Path** are two rows of an app's context menu (`LaunchpadAppMenu`, under Move to category, after a divider) and two VoiceOver actions beside Hide (`LaunchpadTile`), for apps and never for folders. They are on the grid's tiles, the folder cards' and the category cards', on the large icons of a category block (by right-click, as the rest of that menu) and on the unlocked Hidden card, whose menu is Show, Show in Finder, Copy Path (no Move). Their title is the kit's `HelmWord.showInFinder` and the module's `copyPath` ("Copy Path"; the other languages are Finder's "Copy as Pathname" spellings, `N48_V1`, except pt: "Copiar como nome do caminho" is the module's own, since Finder pt_BR's "Copiar como Nomes dos Caminhos" is the several-items form). Copy puts the path string on the pasteboard, as text and nothing else, except that a copy of a hidden app (made from the Hidden card) also carries `org.nspasteboard.ConcealedType` and `TransientType`, each with empty data (`LaunchpadPasteboard`, a board by name like `SystemShotPasteboard`, so `ACopiedPathOfAHiddenAppIsMarkedConcealedTests` reads the types off a pasteboard of its own and never the general one). **Whether a clipboard manager honours the markers was not measured**, and a copied path stays on the pasteboard after the card locks (a known limit). Neither writes a log line. A search has no extra route: it returns no hidden app (`LaunchpadSnapshot.search`).

The two calls reach the Mac through the model's `revealApp` and `copyPath` (`(String) -> Void` and `(String, concealed: Bool) -> Void`, set by `LaunchpadDescriptor`: `HelmReveal.inFinder`, and `LaunchpadPasteboard().copy(path:concealed:)`); the model's own defaults do nothing, so a test never reaches Finder or the pasteboard (`TheSuiteDoesNotTouchTheFinderOrThePasteboardTests`). The window hands them to the state as `onRevealApp` and `onCopyPath` (set and cleared with the window's other closures). **A hidden app's path is offered only by the open, unlocked Hidden card:** `LaunchpadScreenState.fileActions(for:)` is the one maker of the actions, and **the same judgement (`filed(_:)`) runs when the menu is built and again at every press**: it looks the app up by id in the current snapshot, reads whether it is hidden now, and gives the app only if it is not hidden or the Hidden card is open and the gate unlocked. A state with no snapshot, an app the snapshot no longer holds, a locked or asking gate, a closed card and an unlocked gate with another card open get nil at build, so the menu and the actions are not drawn (`AHiddenAppsFileIsOfferedOnlyByTheUnlockedHiddenCardTests`), and a press after the card locked, the app was hidden, moved or removed does nothing or hands the snapshot's current path, never the one captured at build (`AFileActionActsOnlyWhileItsOfferStandsTests`, `AFileActionNamesThePathTheCatalogHoldsNowTests`). `concealed` is decided at the press: the app is hidden then.

**The new dot** is the system blue (`newDotInk` = `Color.blue`) with a thin dark ring (1.5 pt, 2 pt opaque with Increase Contrast; `HelmSignal` has no blue, so the ring is the module's) whose side is 0.14 of the icon, at least 8 pt (`LaunchpadMetrics.newDot(icon:)`), `newDotInset` (0.08) of the icon in from the corner of the icon's frame, which is the corner of the art (an app's art is inset about a tenth of its frame), on an app that `LaunchpadCategories.isNew` says is new: added within `recentDays` (the same test as Recently Added, `isRecent`, now the one place) and with no launch in the counts (`snapshot.launchCounts`, read in `LaunchpadScreen.isNew` from the model's snapshot, so a launch that refreshed the counts takes the dot off at the next draw). Nothing is stored for it, and a new app still lands at the end of the last page (`LaunchpadReconcile`). VoiceOver reads the app's name with "new" (`LpStr.appIsNew`, a full key so each language has its own separator). The dot is on the icon whether names are shown or not, and none is on a folder's tile. Its ring and size were chosen by eye on offscreen shots over a blue icon and a light ground at icon 48, 80 and 128. What was measured (offscreen probes, designer, 2026-11-22): the dark ring against App Store's blue about 3:1 (2.94 to 3.19) at icon 48 to 128, the ring against a light ground 6.2:1, the blue fill against a dark ground 4.5:1; not measured over real glass or with Increase Contrast. "New" counts only launches made from Helm: a launch from the Dock or Finder does not clear the dot.

### The grid settings

The page's Grid section (Automatic with, while it is on, Overall size, Rows, Columns and App icon size while it is off, Show app names, Reset to defaults) is six plain keys in the module's store: `grid.automatic`, `grid.rows`, `grid.columns`, `grid.iconSize`, `grid.showNames`, `grid.sizeMultiplier` (`LaunchpadGridSettings`; deployed stored data, the names never move; a `grid.showNames` that is missing or no bool reads as on, `TheGridSettingsTakeAnyNumberTheStoreHoldsTests`). They are **not sealed**: sealing is for settings that steer unattended work (`Architecture/StoredSettings.md`), these choose a grid with the person present and a forged value only picks a number inside the ranges (rows 2 to 8, columns 3 to 10, icon 48 to 128 pt, whole points; not-a-number is the standard 80), as DisplayCorners' are not. The model reads them in `init`, in `showLaunchpad()` before the window is built and when the page appears, and writes through `setGrid` (clamped, refused when equal, only the changed keys, one log line); never per frame.

`LaunchpadGeometry.make(for:topSafe:settings:)` is pure. **Automatic** (the default) is seven columns and five rows on every screen and is scaled to the screen (§ The grid scales to the screen); **manual** takes the stored counts, at scale 1. The icon asked for is a ceiling: a grid that does not fit shrinks it, `fit(want:columnRoom:rowHeight:names:scale:)` (the column's room and the row's height, each less the chrome: the cell is square), to no less than `iconFloor` (24 pt). **Show app names** (default on) draws or leaves out an app's name under its icon; the folder, category block and Hidden block names stay, and the tile's `.help` and VoiceOver label keep every app's name. A cell is one height for every tile, so names off take one of the label's two lines out (`LaunchpadMetrics.cellChrome(names:scale:)`: 17 pt less at scale 1, `LaunchpadGeometry.names`) and leave one line for the names that stay, which are drawn on one line then (`oneLine`). **Two places keep names with the setting off:** the unlocked Hidden card keeps its app names, and **the Categories view keeps the two lines of label** (`pairedColumns` makes the grid again with names on, from the settings the geometry holds in `asked`, so its blocks, rows and large marks do not shrink); an opened folder or category card follows the setting (`LaunchpadScreenState.namesAsked`). The app tile draws an icon with the room under it empty. The hit maths read the icon's top and size, not the cell's height, so they are the same. Rows, capacity, the shrink-to-fit icon and the large mark all read `names`, and a change re-pages as any grid change does and writes no layout. Reset puts it back on. A label's height does not shrink (at scale 1: 52 pt of chrome a row with names, 35 without), so rows are capped at what the floor icon holds: with names `max(2, height / (24 + 52))`, which binds only on screens under about 770 pt tall (160 pt of top and dots room plus 8 rows of 76), without `max(2, height / (24 + 35))`, which binds under about 630 pt (8 rows of 59); the Categories view always has the first; the window's log line says "N rows asked, M fit". The folder card follows the grid (`columns - 1` columns, `rows - 1` rows to a page, further apps on further pages) and has no setting. A folder's tile shows its first nine apps three by three (`LaunchpadFolderMark`: padding a tenth and gap a twentieth of the well, which is 0.85 of the icon), and the icon cache is bounded to six pages (`6 * capacity`) for the grid's live pages and the card's. **Manual columns are the grid as chosen, to what the screen holds**: a cell is square, so a column is the icon plus the chrome across and a narrow screen holds fewer columns than asked (the icon shrinks first); a long label is cut, scrolls on hover, and its `.help` names the app whole. The page's icon slider publishes the grid while it is dragged and writes the store once, when the drag ends (`commitGrid`).

In the category view the geometry the window reads is the grid's with names on and an even number of columns (`pairedColumns`, § The category view; see "Two places keep names" above), and the stored grid settings are untouched. A changed grid reaches an open window through the model's published `grid` and `LaunchpadScreenState.regrid`: it cancels a lift (a cell address is `page * capacity + slot` and means nothing in another capacity), makes the geometry again, tells the icon cache and cuts the same order into pages again, keeping the page by the choice or by the tile the shown page began with. **A changed grid re-pages and writes nothing** (`ARegridRepagesAndWritesNothingTests`); stored page breaks stay where they are. The panel closes when it loses key, so in use the new grid shows at the next open.

### The grid scales to the screen

**Pass 22, as the old Launchpad did.** Under Automatic the grid is `LaunchpadMetrics.automaticColumns` by `automaticRows` (7 by 5; the category view's paired grid 6 by 5) on every screen, and what changes is how big it is drawn. The scale is `LaunchpadMetrics.scale(for:topSafe:)`:

    s = clamp(min(W / 1440, (H - topSafe - 36) / 864), 0.6, 1.6)

pure and finite for any input (a share that is not a number is 1, an infinite one goes to its end; `AutomaticIsTheSameGridOnEveryScreenTests`). 1440 x 900 with no top strip is exactly 1. **Manual is drawn at scale 1**: `LaunchpadGeometry.scale` is 1 there and the figures below are today's.

- **What follows the scale** (`s`, times the multiplier below): the tile's gap and padding (`HelmSpace.s3 * s`, `s2 * s`, `LaunchpadGeometry.iconTop`, `LaunchpadLabel.sidePadding`), the cell's chrome (`cellChrome(names:scale:)`: three `s3` steps times `s` plus the label's lines at 17 pt times `max(1, s)`), the label's font (the kit's `rowDetail` NSFont size times `max(1, s)`, so the owner's text size still counts and a small screen never gets a smaller label), the search field's top, the gap under it, the dots' room (never less than their bottom offset plus their touch size: `LaunchpadGeometry.dotsRoom(scale:)`, which at a scale under 0.667 would otherwise leave the touch area over the last row) and bottom offset, the page dots (8 and a 24 pt touch size, times `max(1, s)`), the folder card's padding and gap (`LaunchpadGeometry.cardPadding`, `cardGap`: instance values now, the statics are gone). **The pitch is square** (pass 25): a cell is as wide as it is high, `p = icon + cellChrome`, so the gap between columns of icons is the gap between rows; the icon is the least of what was asked, `usableWidth / columns - chrome` and `usableHeight / rows - chrome`, and the grid is `columns * p` wide, centred, so a screen that is wide for its height leaves its sides empty and `cellWidthCap` is gone.
- **What does not:** the search field (280 x 36), the tabs, the card's title and its row of dots, the lift's edge strip and every timing.
- **The multiplier** (`grid.sizeMultiplier`, 0.8 to 1.25, default 1, its own key: `grid.iconSize` is the points Manual asks for and is never read as a multiple; not a number is 1, held to hundredths) is the person's "Overall size", "a little smaller or larger" than automatic. It multiplies **the scale**: everything that follows `s` (icon, label, padding, offsets, dots, card) follows `s * m` (`LaunchpadGeometry.scale`), and the icon asked for is `floor(80 * s * m)`, at most 160 (`automaticIconCeiling`, which `iconRange`'s 128 would otherwise cap; the cache's bound above is for it). **Above 1 it is held** (`LaunchpadGeometry.automaticScale`): the chrome and the offsets grow with the scale as fast as the icon, so on a screen whose height 7 x 5 at x1 fills nearly all of, an unheld x1.25 drew a smaller icon than x1 (123 against 127 pt at 2560 x 1440). The scale is the largest between `s` and `s * m` at which seven columns by five rows still fit the height and the cell's width, never less than `s`. Printed (`AutomaticIsTheSameGridOnEveryScreenTests`): icon at x0.8, x1, x1.25 and the scale x1.25 is held at against `1.25 s` — 2560 x 1440 (top 24) 102, 127, 140 at 1.762 (not 1.997); 1512 x 982 (top 33) 67, 84, 93 at 1.167 (1.312); 1440 x 900 (top 24) 62, 77, 85 at 1.075 (1.215); 1280 x 800 (top 24) 54, 68, 74 at 0.935 (1.071). So x1.25 is held on all four, and reaches its full scale only where the height has room (a 16:9 screen from about 2986 x 1680, the 160 pt ceiling). Below 1 nothing is held: smaller always fits. The ask is stored in `asked` as it was drawn from: Automatic's rows, columns and points are the standard ones and Manual's multiplier is 1, so a value the mode does not read regrids nothing.
- **Fewer than 7 by 5** only where the screen cannot hold them: columns that cannot hold seven square cells at the floor icon (`counts`: `usableWidth / (iconFloor + chrome)`; the icon shrinks first and keeps all seven), rows that the floor icon with its labels leaves no room for (rows at least 2, columns 3 to 7). **Manual's columns are capped the same way** (a stored 10 columns on a 640 pt screen is 7), because a square cell cannot be narrower than the floor icon with its chrome and the grid would leave the screen; before, its cells narrowed to fit. There is no width rule that drops columns for a label: a long one such as German "Festplattendienstprogramm" shrinks to `unbreakableShrink` (0.78), and where that is still wider than the room it is cut and the hover scrolls it.
- **A large block's well meets the visible bodies of the four icons it stands for.** `largeMark` is `2 * cellHeight - chrome` = `p + icon`, the frame's span of two icons (the old width term, `2 * cellWidth - 2 * tilePadding` with the removed `tilePadding`, is never the smaller: the chrome, at least three `s3` plus a 17 pt line per scale, is more than two `s2`, and the cell is square). An icon's visible body is `wellShare` (0.85) of its frame, so the large well's inset from the mark's edge is a small icon's, `icon * (1 - wellShare) / 2` (`LaunchpadGeometry.largeEdge`), not the mark's share: the well is `p + 0.85 * icon`. One function, `LaunchpadFolderMark.inset(_:edge:)`, is read by the drawing (`LaunchpadFolderMark`, `LaunchpadCategoryMark`, `LaunchpadHiddenMark`, each given `edge`) and by hit testing (`frame(ofIcon:size:edge:)`, `frame(ofQuadrant:size:edge:)`, `LaunchpadHit.icon` and `categoryIcon`); a one-cell folder passes none and keeps 0.85 of its frame. At 1512 x 982 (icon 84, pitch 138.6): mark 222.6, well 210.0, from x 33.6 to 243.6 in the block, the same edges as the four icons' bodies (`testALargeWellCoversTheVisibleBodiesOfTheFourIconsItStandsFor`).
- **Hit-testing** reads the same geometry: `LaunchpadHit.at` takes `g.iconTop`, `icon(at:block:mark:edge:iconTop:apps:)` and `categoryIcon` take it as an argument, the card's origin reads the instance padding and gap.

**The header row has one rule.** The search field's top is `topSafe + 28 * s`, the tabs sit on the same row, centred on the field's, and begin at the left edge of the grid being shown (`LaunchpadGeometry.sideInset`: half of what the square columns leave of the width, 271 pt at 1512 x 982, and in the category view, whose 6 columns are narrower than the 7, `pairedColumns` makes it from its own columns). `topSafe` is the taller of the screen's notch room and its menu bar (`LaunchpadWindow.topSafe(safeTop:frame:visible:)`: `max(safeAreaInsets.top, frame.maxY - visibleFrame.maxY)`; the notched built-in reads 32 and 33 on 2026-11-22, so 33). Before, it was `safeAreaInsets.top` alone, which is 0 on a screen without a notch although the menu bar draws over the window there: the row sat 28 pt under the top edge (a few points under the menu bar) on an external display and 28 pt under the notch's strip on a notched one, and the tabs began at a share of the width that the square pitch now moves. The live look on each screen is the owner's, in Helm Dev.

### A cut name scrolls on hover

`LaunchpadLabel.overflow(name:room:scale:oneLine:)` is the one place that says whether a name is cut, pure from the name, the room (`LaunchpadLabel.room(width:scale:)`: the tile's width, `glowSize.width`, a cell's or a large block's two cells, less `2 * HelmSpace.s2 * scale` of side padding, which the tile's own padding reads too) and the scale: 0 where the whole name is drawn; where it is cut, the distance its one line, at the shrunk size (0.85, or `unbreakableShrink` with no break point), has to move to show its end clear of the fade (`LaunchpadLabel.fade`, 8 pt, the fade's width and the scroll's tail). A name that breaks is cut when it needs more than two lines (one under `oneLine`), the others when the shrunk line is wider than the room; 2% is left to `allowsTightening`. The tile asks only while the pointer is on it. While `hovering && !pressed && distance > 0 && !HelmMotion.reduceMotion`, a one-line `Text` at the shrunk size is drawn over the label (which keeps the cell's two lines of height, hidden), left-aligned in the label's room, clipped, with a fade at each end that has more of the name behind it (none at the left before it has scrolled, none at the right once the end is shown); `.task(id:)` waits 0.6 s, moves it by `HelmMotion.marquee(distance:)` (linear, 40 pt/s, never under 0.3 s), holds 0.9 s and returns by `HelmMotion.interface`. The pointer leaving, a press or Reduce Motion ends it (the label is drawn as before and `.help` names the app whole). Nothing measures a view: `TheLaunchpadWindowMeasuresNothingTests` bans measuring and the scroll is one state change under `withAnimation`. Tests: `LaunchpadLabelTests` (optional).

### Lifting a tile

A tile is lifted with raw mouse events, not SwiftUI's drag and drop (the source folder bans those words, `TheLaunchpadWindowMeasuresNothingTests`), and nothing is measured. `LaunchpadPanel.handle` converts a left press, drag and release to the window's top-left coordinates and gives them to `LaunchpadScreenState` (`pointerDown/Moved/Up`); it swallows a press only when the state says it began on a tile and a lift is allowed (`liftAllowed`: the grid shown, with no search text, no name being typed, no launch under way and the window shown; a press in an open folder's card is a lift too), so the background tap, the dots and the search field keep working, and while a press is held it swallows the wheel, the right button and every key but Esc. A press let go without moving is a click on that tile (`.click`: launch, or open the folder); the press wash is `state.pressedID`. **No lift in the category view**: `beginLift` refuses there (§ The category view), so a press on a block is a click only.

`LaunchpadLift` (pure struct, `Sources/Modules/Launchpad/UI/LaunchpadLift.swift`) is the machine: `feed(input, at:, surface:, time:)` returns **one** effect (`none`, `lift`, `moveGap`, `arm`, `turn`, `newPage`, `openFolder`, `closeFolder`, `release`, `cancel`, `click`) naming **cell addresses** (`page * capacity + slot`), and `wake` says when a tick would change something. `LaunchpadHit.at` finds what is under a point from `LaunchpadGeometry` and the cells each page's tiles cover (`LaunchpadSurface.slots`) alone (a tile's core is the middle 60% of its width and the icon's height; the rest of the cell is its margin; the strip along either side is an edge). The numbers are `LaunchpadLiftTiming`: 5 pt to lift, 0.12 s in a margin before the gap moves, 0.30 s in the icon before a drop goes onto it, 40 pt edge, 0.6 s then every 0.9 s to turn the page, on the last page to make a new one. **The pointer over the gap itself changes nothing**, and the gap goes only by dwell, so a hundred moves inside a cell publish nothing.

The state holds a preview (the pages' segments with a `LaunchpadEntry.gap` of one stable identity where the carried tile was) and publishes only `lift` (the carried entry and the armed target; changes per slot or target) and `pages`; the pointer's place is `liftPoint`, a separate object read only by the overlay (the carried tile at 1.08, none under Reduce Motion, one `.offset`, no hit testing). One `@MainActor` task is armed for the sooner of `wake` and `stuckWake` and cancelled by `shutdown()` (window close); `stuckWake` is `LaunchpadLiftTiming.stuckCheck` (0.5 s) after the machine's last input while a press is engaged, so a mouse-up that never came is found by the tick's left-button read, and each tick moves it on (no zero-delay loop). The gap's id is `LaunchpadEntry.gapID`, a leading space, which no bundle id can spell, so an app named `gap` is not the gap. A release maps to a drop by anchors (`.beside` the neighbour in the gap's segment, `.onto`, `.newPage` when the gap is alone on the last page), `LaunchpadLayout.edit` makes the edit or nil, the page shows the result at once and `LaunchpadViewModel.place` writes it and answers the snapshot shown; a new folder opens when it lands. Nothing is written on Esc, an abort, the window closing, a left button not down on a tick, a search typed, or the carried app vanishing from a new snapshot (a snapshot that keeps it keeps the gap by its neighbour). Pages are the layout's items cut at `.pageBreak`, then by capacity (`LaunchpadPaging.pages`); a tile's index for the arrow keys is counted over the whole list (`pageStarts`).

**Folders in the lift.** A folder tile is a target twice: held 0.30 s on its icon it is armed (a release adds the app), held 0.70 s from arriving on it (`folderOpen`, counted from arrival like the 0.30 s, not from the drop being armed) its card opens (`LaunchpadLift.Effect.openFolder`, only when the carried tile is an app: folders never nest) and the same machine goes on against the card: `LaunchpadSurface.card` (`LaunchpadSurface.Card`, the rect of `LaunchpadGeometry.card`, shared with the drawing) makes `LaunchpadHit.at` answer with the card's tiles (index in the card, never a core, so nothing is armed), its empty cell, or `away` outside the card inflated 12 pt (`cardMargin`). The gap in the card is a `LaunchpadEntry.gap` in `cardEntries`, moved by the same margin dwell. **A card with pages turns them at its sides**: `LaunchpadHit` answers `edge(-1)` or `edge(1)` over the strip left and right of its tiles (the card's padding and the 12 pt margin ring, its whole height), and the same edge dwell (`edgeFirst`, then `edgeRepeat`) turns the card's page, never past its first or last page (the grid's last page makes a new one; a card's does not). A turn moves the gap onto the page now shown (`seatGap`: the nearest place on it, so the carried tile has a seat where it arrived), as does a snapshot that lands mid-lift; and a release is in the card when the pointer is on the card or on one of its edge strips, landing where the gap is on the page shown. The card closes (`closeFolder`) after the pointer has been **outside for 0.25 s (`leaveCard`) and only once it has been inside**: a card opens at the window's middle, not under the pointer that opened it, and without that rule it would close at once and open again. The lift goes on with its source (`LaunchpadDropSource.top`, or `.folder(id)` when lifted from inside a card, which a press on a tile of the open card does; a card with pages is lifted from like any other). Release inside the card is `.intoFolder` (an add, or `moveInFolder` for a member), anywhere else the card closes first and it is a drop on the grid, `.beside` / `.onto` / `.newPage` with the source: a lift from a folder gives the grid a gap right after the folder's tile, whose tile meanwhile shows the folder without the carried app (the engine dissolves a two-app folder when the edit lands). Esc ends a lift and leaves the card open.

**Large folders in the lift.** A cell address stays `page * capacity + index of the tile on the page`, a tile's index and not a cell's number, because a block covers four cells and is one tile; the hit test finds the tile covering the cell under the point. A large block is core all over (no margin ring), so a small app held over any part of it arms it at 0.30 s and opens it at 0.70 s, as a small folder; the gap moves by hovering the neighbours. An empty cell, a hole beside a block too, is the end of its page. **The gap is as big as the tile carried** (`publishPages`: the gap counts as large while a large folder is carried): the block's landing place depends on its neighbours, so a gap of one cell would show a place where the block does not land; a carried folder over a block can only reorder by dwell, as over any tile. `ADropLandsWhereTheGapShowedTests` compares the shown gap's page and cells with where the tile landed. The panel handle, `liftAllowed`, `pointerBusy` and the right button are unchanged; an inner icon's click is the state's (§ The window).

**The name.** The card's title is a `TextField` bound to `state.nameDraft`; `state.renaming` follows its focus (the view keeps both in step). While it is true `LaunchpadPanel.handle` asks `state.handleNameKey` first (after the marked-text and modifier guards): Return commits (trimmed, written through `LaunchpadViewModel.rename` only when it changed; blank reverts locally), Esc reverts and leaves the folder open, **every other key returns false** so the caret, the arrows and the typing are the field's. Closing the card commits a changed draft. Esc order: a lift, the name field, the folder, the search, the window. A folder just made opens with the field focused and its text selected (`beginRenaming(selectAll:)`, `TextSelection`).

**Reordering by key and by VoiceOver.** The same drop, with no pointer: Option+arrow moves the chosen tile one place (Left and Right in the flat drawn order, a large folder one stop; Up and Down to the tile the arrow itself would choose, `arrowTarget`), Option+Shift+arrow combines it toward that neighbour (an app onto an app makes a folder, onto a folder joins it) or, in an open card, takes the app out. Each chord is one written edit; the reverse chord restores the order after a plain move, but not always (Down onto a short last row does not come back by Up), and no chord restores a combine or a take-out; there is no pick-up mode, and a plain move never makes a folder. `LaunchpadKeyMove` (pure, `Sources/Modules/Launchpad/UI/LaunchpadKeyMove.swift`) turns the drawn order into a `LaunchpadDropDestination` by anchors, `.beside(neighbour, after:)`, never an index of the layout (the window draws a subset of `layout.items`: a stored page break is not drawn); `LaunchpadScreenState.reorder(tile:_:)` is the one entry, keyed by the tile and not by the choice, asks `LaunchpadLayout.edit(dropping:)` for the edit the matching drop makes and writes it through `place`. No engine code and no `.move(toIndex:)`. **Across a stored page break** the tile lands on the near side of the page it enters, first on the next or last on the previous, and the break stays; where a page ends only because it is full, the plain neighbour anchor gives the same landing once the page is cut again by capacity; no page is made by key, and Right on the last tile does nothing. **A folder never nests**: `combine` refuses a carried folder in the pure type, since `edit` would silently make a `.place` of it. **Take-out** is source `.folder(id)`, destination `.beside(folderTile, after: true)`: the card closes, the app lands right after the folder's tile and stays chosen, a two-app folder dissolves in the engine as for a drag. The chord is the state's only when `reorderAllowed` (`liftAllowed`, so no search text, no name being typed, no launch under way; not the category view, so neither the Hidden card nor a category block's card; no press on a tile; no write in flight, `placing == nil`). With a press on a tile (`pointerBusy`) `LaunchpadPanel.handle` swallows every key but Esc before the chord is looked at (`LaunchpadWindow.swift`); in the other refusals `reorderKey` returns false and the key goes on to the field as before, so a key during a write is dropped, not queued. After the answer the choice follows the tile by its id and the page is set to the page of its new place (the card's page by `goCard` in a card), under the reorder curve armed by `animateNextUpdate` (instant under Reduce Motion). VoiceOver gets the same moves as custom actions (`LaunchpadTileMoves`, built by `state.moves(for:)` from the same plan, an action only where the move exists, and for an add to a folder only where its edit exists: a full folder offers none; each action carries the destination and the folder-or-app it was read on and is refused at run when the plan then differs): Move earlier, Move later, Move to previous page, Move to next page, Put in folder with previous or next app, Add to previous or next folder; in a card, Move earlier, Move later, Take out of folder. After each move `HelmA11y.announce` says the place and page from the new snapshot, or that the tile cannot move (at an edge, or where its edit is refused); a tile no longer shown is announced as nothing, never by its id. A combine that makes a folder opens its card, and the page shown is already the folder tile's page, so closing the card leaves the choice on a page that is shown. `AKeyOrAnActionMovesATileAsTheDropWouldAndLosesNothingTests` and `AKeyDuringAWriteOrWhereNothingIsArrangedWritesNothingTests` pin that every chord writes the drop's own edit, that nothing is lost across a break, that a folder never nests, that a take-out loses no app, and that nothing is written where there is no arrangement or while a write is out; `TheChoiceAndThePageFollowTheMovedTileTests` (optional) pins the choice and the page.

## The category view

The person chooses Apps or Categories by the switch in the window; the choice is a plain key `view.mode` ("apps" or "categories"; missing or any other value reads as apps) in the module's store, **not sealed** (it steers nothing unattended, as the grid keys), read in the model's `init` and in `openWindow()` beside the grid, never in a SwiftUI initial value, and written through `setViewMode` (refused when equal, one log line carrying the view). `LaunchpadViewMode` is in `Sources/Modules/Launchpad/UI/LaunchpadViewMode.swift`.

**A block is a folder-shaped entry.** `LaunchpadCategories.blocks` (pure, `Sources/Modules/Launchpad/Engine/Logic/LaunchpadCategories.swift`) turns the visible apps, the counts and the clock into blocks; the state holds each as `.folder(id:name:apps:large: true)` with `categoriesShown` set, so placement, paging, the hit test, the card, its pages and Return are the large folder's, unchanged. Each block's id is fixed and the same in every language (derived from the block's kind; a kind added at the end never renumbers one), because `reflow` reopens an open card by id and a random id would close it at every snapshot. What keeps a block from being a folder is the mode: no lift begins, no rename (the title is a plain `Text`), no resize item, no `onPlace`, `onRename` or `onResize` call, and `TheCategoryViewWritesNoArrangementTests` pins that no lift, rename, resize or drop reaches the layout. Hide (the block card's tiles' menu) does write the hidden list, as the owner chose: it is the person's own edit, and the order and arrangement stay untouched.

**What is in a block and in what order.** An app is in the block of its `public.app-category.*` value; a value that is unknown or not of that family goes to Others, empty blocks are omitted, and a hidden app is in none. "Recently Added" is first and only when it has an app: an app added within 30 days (`LaunchpadCategories.recentDays`; a date in the future or none is not recent), newest first, and it stays in its own category too. The other blocks go by the total of their apps' launches, most first (a saturating sum), ties by the localized name, then the kind; Others is last whatever it counts. Apps inside a block go by their own count, ties by catalog position. A block of four apps or fewer draws each as a large icon; from five, apps one to three are large and the fourth cell is the cluster of four tiny icons of apps four to seven, which opens the card. A press on a large icon launches it, a press anywhere else on the block opens the card. The names come from `LaunchpadCategoryName.title(for:)` (the system's own spellings; "Categories" and "Recently Added" are from the displayed tables of Podcasts and Maps).

**Move to category.** Every app's context menu (`LaunchpadAppMenu` in `Sources/Modules/Launchpad/UI/LaunchpadTiles.swift`: Hide, and the submenu "Move to category") has the app's own category as an undo row on top, disabled while the app is not moved, and the 28 categories by their title in the person's language with "Others" last (`LaunchpadCategoryName.choices`, not cached, the language can change); the category the app is in now is checked. It is on the grid's tiles, on a folder card's and a category card's tiles, and, by right-click, on the large icons of a category block (which therefore has Hide there too); it is not on a large folder's mini icons in the grid, nor on a control-click, which is a left press in this panel as it is for Hide. A VoiceOver custom action cannot be a submenu, so Move is reached through the context menu (VO-Shift-M) and Hide stays an action as well, on the grid's and the cards' tiles; a category block's large icons have no Hide action and no tile-level menu for VoiceOver (the block tile has `hide: nil`, the menu is on the inner image), so VoiceOver reaches those apps through the block's card. `LaunchpadCategories.blocks` takes the overrides: a moved app is in its target block and no other, Recently Added still by its date, a hidden app in none, its launches go with it so the blocks may reorder. The state publishes `moved` from the snapshot (the menus' check marks read it; the snapshot itself is not published) and `move(_:to:)` arms the next reflow's reorder curve in the category view only and only when the request changes the state's own record (a move to the category the app is in, or the return of an app that is not moved, is refused by the engine and arms nothing, since no update would spend the flag), so the app leaves one block and enters the other under `HelmMotion.reorder` (instant under Reduce Motion), while the grid changes no page. An open card of the block the app left stays open by its fixed id; the card of a block the move emptied closes as it does for Hide. `AMoveShowsInTheRightBlockAndNothingInTheGridChangesTests` pins this.

**Paired columns.** A block is two cells wide, so in this view `geometry` is `gridGeometry.pairedColumns` (the grid made again with names on, `columns` rounded down to even and `capacity` made again; an odd grid leaves its spare column empty, so blocks centre). The state keeps both, `gridGeometry` the real one and `geometry` what everything reads, and `icons.reconfigure` is not called (the cache limit `6 * capacity` still holds). **A search is flat**: while the field holds text the geometry is the grid's own and the hits are the apps.

**The counts file.** The launch counts file sits beside the layout in its private folder (0600 in a 0700 folder): version 1 and a count for each bundle id. One shared ceiling (`LaunchpadLimits.maxLaunchCount`, with `maxApps` entries, the id length and `maxFileBytes`) bounds it; a value that is no finite number is dropped, any other is clamped and rounded down, a count of 0 is not stored, `record` saturates, and any version but 1 is unreadable. An unreadable file reads as no counts (the window never breaks; the order falls back to the catalog's) with one warning for each distinct bad file and no id in it; the first `record` or reset moves it aside once to the same name with `.unreadable`, and when that fails nothing is written. A read never writes. One lock covers read, bump and save together, and the engine's lock comes before it. A count of an uninstalled app stays until the size cap and is never shown, as the UI reads counts only for installed apps.

**The setting's Reset row.** The page's row after the Grid section (title, a note and a "Reset launch counts" button, `LpStr`; the bare "Reset" is the host's `resetSection`, and one English text is one key) calls `resetLaunchCounts`, with no dialog (counts cost nothing to relearn) and is disabled when `snapshot.launchCounts` is empty; the model reads again after a launch, so a launch counted while the page is shown enables it.

## The Hidden block

In the category view the last block is "Hidden", drawn as a lock with no icons and no count (`LaunchpadHiddenMark`). It is not a `LaunchpadCategoryBlock.Kind`: the blocks are engine output computed from visible apps, and a hidden app never enters it. `reflow` appends a UI entry with the fixed id `LaunchpadHiddenBlock.id` (its own, not built from the blocks' prefix: their kind byte runs 0 to 29, and this id is distinct from every one of them) and `apps: []` always, so while locked no hidden name is in `segments`, `top`, `pages` or the icon cache. Hidden names exist only in `folderApps` and `cardEntries` of the open, unlocked card, read from `LaunchpadSnapshot.hiddenApps` (installed, in catalog order). A hidden app is in no search (`LaunchpadSnapshot.search` filters it out) and in no log line: the gate's lines are fixed words.

**The lock** is `LaunchpadHiddenGate` (`Sources/Modules/Launchpad/UI/LaunchpadHiddenGate.swift`): `locked`, `asking`, `unlocked`, in memory only, one gate for each window state and one for each settings page. It asks a `LaunchpadAuthPort` (`Sources/Modules/Launchpad/Engine/Ports.swift`, whose doc comment names which reasons fold into each of `success`, `failed`, `cancelled`, `unavailable`); `SystemLaunchpadAuth` (`Sources/Modules/Launchpad/Engine/SystemPorts.swift`, the one file that imports LocalAuthentication) asks `deviceOwnerAuthentication` with a fresh context and a reuse duration of 0, so the system draws the dialog and Helm never sees a password; a test process answers `.unavailable` (`TheSuiteDoesNotAskForTouchIDTests`). Only `.success` unlocks. `ask` does nothing unless locked (one prompt at a time); each ask carries a ticket that `lock()` bumps and the result is read once on the main actor, so an answer that comes after a lock, a close or a newer ask is dropped; cancelling the asking task invalidates the context. Only `unavailable` shows the banner "Hidden apps need a Mac password or Touch ID."

**What closes it.** `open(folder:)` is the one way in (a click, Return, the tile's button and VoiceOver reach it). `closeFolderQuietly()` locks when the open card is the Hidden one, which covers Esc, a click on the background, the other view, a typed search and a vanished folder; `open(folder:)` locks when another card replaces the unlocked Hidden one; `shutdown()` locks and closes it, which covers the window closing, a successful launch from the card and the toggle; the gate also locks by itself after 90 s of an unanswered prompt (the system's dialog is dismissed), and a lock of an unlocked gate drops a notice that names an app (`onLocked`, `LaunchpadViewModel.dropNamedNotice`; a failed launch from the card names a hidden app); the settings page locks in `onDisappear`. In the card the app menu and VoiceOver offer "Show" (`onUnhide`, the model's `unhide`), Show in Finder and Copy Path (§ Show in Finder, Copy Path and the new dot; this card is the only place a hidden app's path is offered) and no Move; launching works. The gate is a UI-level guard: `LaunchpadViewModel.launch` and `unhide` are not gated, so an external caller must be gated first. It is not encryption: `layout.json` still names the hidden ids and Finder and Spotlight still find the apps.

## The Dock icon

Helm has no Dock icon, so Launchpad's is a second, tiny app nested in the bundle: `Helm.app/Contents/Helpers/Helm Launchpad.app` (Helm Dev: `Helm Dev Launchpad.app`), the target `HelmLaunchpadHelper` (`Sources/HelmLaunchpadHelper/main.swift`). The person drags its icon from the settings page to the Dock (the row also has "Show in Finder"; it is hidden when `AppBuild.launchpadHelperURL` is nil: `swift run`, a test host, a bundle packaged before the helper). A click starts the helper, which opens `helm-launchpad://toggle` at one explicit application, the Helm it sits in, without activating it, and quits. **Its shown name is the word for "Apps" in each language**, not its file name: `Resources/HelmLaunchpadHelper/<lang>.lproj/InfoPlist.strings` (`CFBundleDisplayName`, `CFBundleName`) with `LSHasLocalizedDisplayName`, copied into the bundle by `package-app.sh`. The words are the ones macOS's own Applications folder shows (`/System/Library/CoreServices/SystemFolderLocalizations/<lang>.lproj`; the system's tables for pt-BR and zh-Hans are `pt.lproj` and `zh_CN.lproj`): en and fr "Applications", de "Programme", es "Aplicaciones", ja "アプリケーション", zh-Hans "应用程序", pt-BR "Aplicativos"; ru is the owner's word, "Приложения" (macOS says "Программы"). Helm Dev shows "<word> Dev" (`rewrite-as-dev.sh`). The settings page names the helper by what Finder displays (`FileManager.displayName`) in the icon's and the button's VoiceOver labels. It is an accessory app that never shows a window and never activates, so the panel's "another app came forward" ender ignores it by bundle id (`LaunchpadWindowEnders`) and the click closes the window by toggling it.

**The link is input from outside the process**, so `LaunchpadLink.accepts` (`Sources/HelmRuntime/LaunchpadLink.swift`) compares the spelling `URL` gives back (normalised: `URL(string:)` drops invisible host characters such as U+200B, U+00AD and the byte-order mark, so a link that reads as the exact one after that is accepted, and the result is still only the toggle) with `<scheme>://toggle`: another scheme or host, a path (even `/`), a query, a fragment, a user or a port is refused, and `ModuleHost.openLaunchpadFromLink` logs one `link refused` line without the URL (one per throttle window, so a loop of bad links does not fill the log). Links closer than 0.5 s to the last accepted one are dropped (`LaunchpadLink.Throttle`), so a double click does not open and close the window. An accepted link presses the descriptor's own shortcut action, `hotkeyPressed`, so the Dock and the shortcut cannot disagree. With the module off the same link logs `link: module is off` and posts `.helmOpenSettings` for the Launchpad page, the way the status item does.

**One helper per channel.** The release helper's bundle id is `com.helm.app.launchpad` and its link scheme `helm-launchpad`; Helm Dev's are `com.helm.app.dev.launchpad` and `helm-dev-launchpad` (`AppBuild`). The helper's plist names its parent (`HelmParentBundleID`) and its link (`HelmLaunchpadURL`); the parent is the bundle three levels up when its id matches, else the app LaunchServices knows by that exact id. So a Helm Dev link never wakes the release. `Scripts/rewrite-as-dev.sh` rewrites all of it for Helm Dev, and a test reads the pair, and the shown names in every language, back from the staged and the rewritten bundle.

**Why Helm does not write the Dock.** A pin is the person's own, put there by dragging the icon (or by Keep in Dock), so nothing writes `com.apple.dock`, nothing restarts the Dock and nothing is left behind to remove. The cost is a stale pin when Helm moves: the Dock keeps the old path and the person drags the icon again; the page says so.

**The panel sits just below the Dock.** The window's level is `CGWindowLevelForKey(.dockWindow) - 1` (`LaunchpadWindow.level`): above every ordinary window, under the Dock, so the Dock draws over the panel and the pinned icon stays clickable, as macOS's own Launchpad leaves it. The frame is still the whole screen, and the menu bar, which is above the Dock's level, draws over the top strip.

**A limit: over a full-screen app the Dock stays hidden.** Over a native full-screen app (its own Space) the Dock is not drawn when the panel opens, whatever its autohide setting, because a full-screen Space hides it; on a normal desktop it draws over the window as above. Helm cannot show it from there: `NSApp.presentationOptions` can only hide the Dock more, activating Helm with it set to `[]` left the Dock hidden, moving the pointer to the screen's bottom edge (`CGWarpMouseCursorPosition`) did not bring it, and no public or transient private call that reveals it was found; the calls that would persist (`CoreDockSetAutoHideEnabled`, writing `com.apple.dock`, restarting the Dock) change the person's own setting and would not help in a full-screen Space, so they are not used. The old Launchpad was the Dock's own window and never met this. Measured 2026-11-22 on macOS 27.3, Helm Dev 2062; the owner chose to leave it.

## The trackpad pinch

Four or five fingers brought together on a trackpad **scrub the window open**, spread they **scrub it shut**: the window's fade and the grid's settle follow how far the fingers have come, and letting go completes the gesture at the midpoint or on a quick flick and otherwise puts it back (`LaunchpadViewModel.pinched(_:)`; a pinch with the window open brings it forward, a spread with none open does nothing). **Off by default**: a plain key `gesture.pinch` in the module's store (`LaunchpadPinchKey`, deployed data, the name never moves), not sealed, since it steers nothing unattended and a person is at the trackpad. **Reduce Motion** follows nothing: the window opens or closes at once where the gesture reaches progress 1 or, short of that, ends complete (released past the midpoint or flicked), unless it already did.

**The route.** The fingers come from MultitouchSupport, a private framework with no header, behind `TrackpadTouchPort` (`Sources/Modules/Launchpad/Engine/Ports.swift`; the doc comment of `TouchWatchStart` in the same file names three answers a port gives (watching with a device count, no trackpad, the framework or a symbol missing) and a fourth, a layout refused, that only the engine records). `MultitouchSupportPort` (`SystemPorts.swift`) `dlopen`s it and `dlsym`s five symbols, as `DisplayCorners` does for `CGSetLocalEventsSuppressionInterval`, so a macOS that moved it is `.frameworkMissing` and never a crash. A tap or a global monitor was ruled out: the system's gestures travel as a Dock event whose encoding changed in macOS 27, and an event carries no finger count. The framework wants no permission and Helm declares none (`permissions: []`); this is read from other projects' notes and was not tried against a denied Mac.

**The layout is not trusted.** A record is read at a fixed stride (96 bytes: state at 20, normalized x and y at 32 and 36, each read unaligned) and every frame goes through `TouchFrame.init?` (`Sources/Modules/Launchpad/Engine/Logic/TouchFrame.swift`): a count outside 0 to 10 is refused before any record is read, a position that is no number or lies outside -0.05 to 1.05, a state outside 0 to 7, a time that is no number. `FrameTrust` counts refusals in a row; at 30 the port drops every frame and tells the engine, which says `layoutRefused` once and stops the watch (a stand-down carries the number of the start it came from, so a module that came back in between keeps its new watch). The person's switch turned off and on, or the module activated again, watches anew. A test process answers `.noTrackpad` and calls nothing (`TheSuiteDoesNotWatchTheTrackpadTests`). On wake the port restarts its devices (a pad may have gone and come back).

**The recognizer** (`Sources/Modules/Launchpad/Engine/Logic/PinchRecognizer.swift`) is a value fed frames of one pad; `feed` answers a `PinchEvent` or nothing, at most one a frame: `began(direction, progress:)`, `moved(progress)`, `ended(complete or revert)`. A session starts when 4 or 5 fingers are down and arms when they have held within `landedMovement` for `landedFor`. Progress is the smaller of the ratio's share and the distance's share of the way from the dead zone (`beginRatio`, `beginSpreadRatio`, `beginChange`) to where the one-shot pinch fired (`pinchRatio` and `minChange`, `spreadRatio` and `minChange`), 0 to 1, so it reaches 1 exactly where pass 10 fired; the direction is the sign of the change when the scrub begins and fixed after it. A scrub **begins** when progress has stayed at least `beginProgress` for `beginHold` with the spread change at least `swipeShare` times the centroid's travel (a swipe moves the centre more than it changes the spread) and not before; `armedLimit` applies only until then. `moved` follows a change of `progressStep`, and always 0 and 1. The scrub **ends** when every finger lifts, a finger more or fewer comes inside 4 to 5, the count stays out of 4 to 5 past `countGrace` (frozen meanwhile, resumed if it comes back), it is `scrubLimit` old, a pad clock runs backwards or the swipe rule (the centroid travelling `swipeTravel` with the spread unchanged, which is a Spaces swipe) says so. The outcome is `complete` from `commitAt`, or from `flickFloor` when progress rose at `flickSpeed` over the last `speedWindow`, and otherwise `revert`; a lift, a changed count and a count out past the grace judge by the progress they had (the speed is of the moments before the end, or before the count left); a swipe, a clock that runs backwards and a scrub past its limit revert. After any end it says nothing until every finger lifts. Time is the frames' own. **Every number sits in `PinchThresholds` and is an untuned guess**; the engine keeps one recognizer per pad, so two pads are never one hand.

**Lifetime.** Every call that starts or stops the port goes through one lock (the engine's `deinit` stops it without the lock, when nothing else holds the engine), and a stop decided for an old watch is dropped if a newer start has begun (a stop that finds a start still in flight leaves the port to it). Every start takes the next generation number; a frame and a stand-down are dropped when their start is no longer the current one, and a start that returns after `deactivate()` is stopped at once. `LaunchpadEngine.activate()` asks the switch (`pinchEnabled`, read from the store each activation) and starts the watch only if it is on; `deactivate()` and the engine's `deinit` stop it; a second start while watching does nothing. A count that changes inside 4 to 5 re-lands the hand, and a pad clock that runs backwards starts a new session. The frames arrive on the framework's thread and are fed to the recognizers under the pinch's own lock (`pinchLock`, apart from the layout's, which a disk read holds: main and the framework's thread never wait on it; order `portLock`, then `pinchLock`). What a recognizer says goes to a **mailbox** under that lock and main is told once (`drain`, which reads `onPinch`, set by the descriptor to `model.pinched`, where it delivers): a `moved` replaces a `moved` at the end of the mailbox, so a busy main holds a few events and not a hundred frames a second. **One scrub at a time**: the pad whose `began` came first owns it, and another pad's `began` is dropped and so is all it says after. **A scrub that main was told began is always told it ended**: a watch that stops inside one (the switch off, `deactivate()`, a stand-down) drops the mailbox from its first undelivered `began` on, keeps what comes before it (an `ended` main is owed) and puts `ended(.revert)` after it under the same lock; so does a pad that falls silent: no frame from the scrub's owner for `silenceLimit` (0.5 s, checked every 0.25 s on the engine's injectable clock) reverts the scrub, and the pad's later events are dropped because it no longer owns one. A scrub that main was never told of is dropped whole, with an `ended(.revert)` main ignores. The log has a line at start (devices watched), at stop (frames delivered, scrubs begun and completions: a zero frame count is a watcher that went deaf) and at each stand-down, one when a pad falls silent in a scrub ("pinch: a trackpad went silent in the middle of a scrub; the scrub was reverted") and one when the Mac wakes ("pinch: the Mac woke, trackpads gone" or "watched again"); a Mac with no trackpad logs one line when the switch is on. The owner tunes `PinchThresholds` by hand from those lines.

**The model and the window.** `pinched(_:)` keeps one `Scrub` (none, opening, closing, forwarding, reduced, spent) from `began` to `ended`. A pinch with no window builds one (as `showLaunchpad` does, through `openWindow`), never `present()`s it, and hands it `beginScrub(.pinch)` and then each progress; a spread with a window open does `beginScrub(.spread)`; a pinch with the window open only brings it forward if it completes. An end that **opens** completes the window (`endScrub(.complete)`: key and search focus at once, settle to whole, clicks ignored until the settle arrives, as in `present()`); the content draws only the zoom, the panel's alpha carries the fade; one that **reverts** an opening makes the model forget the window first and then closes it; a closing that completes is forgotten first, too, and one that reverts leaves it. The window's `onClose`, the shortcut (`closeLaunchpad`), `stop()` and a second `showLaunchpad` all set the scrub to none, so what the fingers say later reaches no other window. The scrubbed window is shown **without becoming key** (`orderFrontRegardless`, `ignoresMouseEvents`), so the app in front keeps the keyboard until the scrub completes; the Space changing, another app coming forward and the screens changing close it as they close any window (a Spaces swipe shows nothing), and the Mac going to sleep closes a half-open one and puts a half-closed one back (`LaunchpadWindowEnders`, `willSleep`). Not tried on a pad: that a panel ordered front at alpha 0 is composited and ticks its display link, that the search field takes the keyboard when the panel becomes key after the screen appeared, what the frames do while the fingers hold still, and the cost of the alpha at 120 Hz.

**The system's own pinch.** Helm writes no trackpad setting. `SystemTrackpadPreferences` (`SystemPorts.swift`) reads `TrackpadFourFingerPinchGesture` and `TrackpadFiveFingerPinchGesture` from `com.apple.AppleMultitouchTrackpad` and `com.apple.driver.AppleBluetoothMultitouch.trackpad` (2 was read on macOS 27; 0 is taken as off, unverified). The doc comment of `SystemPinch` says what `unreadable` collapses: a missing key or domain, a value that is not a number. While the switch is on and the system's pinch is `on`, the page says so and offers "Open Trackpad Settings" (`PermissionCheck.openTrackpadSettings`, the extension's own identifier `com.apple.Trackpad-Settings.extension`, read from `TrackpadExtension.appex`; More Gestures is a tab and is not addressable), because a passive listener cannot stop the system opening Apps over the window.

## The Launchpad settings page

The page id is the module id, `launchpad`. A grouped form: a button that opens the window, the Dock-icon row (below), the shortcut's row (a taken combination is said), the pinch row (§ The trackpad pinch: a switch, a state line while it is on, and the system's own pinch if that is on too), the grid (§ The grid settings), the hidden apps' row (behind the same lock, asked for by Show; § The Hidden block), and "Reset arrangement", which asks first: the press sets `pendingReset` and only the dialog's destructive button resets, once, keeping what is hidden and what is moved (`LaunchpadEdit.resetArrangement`, reconciled in the engine so every shown app is back in the default arrangement, § The default arrangement). A notice banner above, no button: an app that is no longer installed, one that could not be opened, an arrangement that was not saved; it has no timer, and a launch that succeeds, a hide or a show, and the next appearance clear it.

The "Moved apps: N" row, in the section of the launch counts, has a "Return all" button, disabled at 0, which is one `.returnAllToOwnCategory` edit and so one write; N counts the snapshot's moves, an installed app or not until a complete read drops it.

After the grid comes the Reset row for the launch counts (§ The category view); the switch's choice is not on the page, it is the window's.

The Dock-icon row is there only when the helper exists (`LaunchpadViewModel.helperURL`): the helper's own icon (`HelmDraggableFileIcon`, the kit's, dragged out as a file URL), a title, one sentence and "Show in Finder" (`HelmWord.showInFinder`, `HelmReveal.inFinder`, reached through the model's `revealHelper` that the descriptor sets, as `present`). § The Dock icon.

A state of the page is shot with `bash Scripts/shoot.sh launchpad ... --name <state>-<light|dark>` as the Disk page's states are (§ The states of the Disk page in `Architecture/Disk.md`). The window is shot live in Helm Dev, and nothing on the Mac is launched or removed to reach a state.

The hidden apps are behind the same lock: a row "Hidden apps: N" with Show (`LpStr.hiddenAppsCount`, no names) asks Touch ID or the password, and then the list with its Show buttons is drawn until the page goes (`onDisappear`).

**The window's top and the grid** (`LaunchpadGeometry.make`, `LaunchpadMetrics`). The search field is 36 pt high (`searchHeight`, the kit's header controls), 32 pt (`gridGap`, no `HelmSpace` step: s7 is 28, s8 is 40) above the grid's start; the rows are counted in what is left under that start less the dots' room, and the room they leave over is shared half above, half under, so `gridTop` is the start plus half of it (at a size where the rows fill the room it is 96, as before). Hit tests, the card's origin, the lift and the dots read `gridTop`, so they follow. A tile chosen by the keys has the glow, or, when the glow is off (Reduce Motion, Increase Contrast, shader not compiled), a 2 pt ring of white 0.6 on the tile's rounded rectangle, so chosen is not the pressed wash. The search placeholder is white 0.75 (about 5:1 on the capsule over a dark wallpaper, measured offscreen). The fills are `LaunchpadMetrics.wellFill`, `fieldFill`, `secondaryInk`, `placeholderInk`, `scrim`, `unlitDot`.
