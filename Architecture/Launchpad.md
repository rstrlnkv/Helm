# Launchpad

`Sources/Modules/Launchpad/` is an app launcher: what is installed, how the person arranged it, what they hid. The engine (`Engine/`) reads, edits and launches; the UI (`UI/`) is a full-screen window the person opens with a shortcut they record, and a settings page, registered in `Sources/HelmApp/ModuleRegistry.swift` (`LaunchpadDescriptor`). The reasons live on the doc comments of the code that carries them:

- an app is its bundle id and nothing else is stored; a path belongs to the latest catalog read, so a planted layout file cannot make Helm launch a path: `Sources/Modules/Launchpad/Engine/Logic/LaunchpadLayout.swift`;
- the three roots, the walk judged by name and one `lstat`, the duplicate rule (earlier root, then smallest path), and why Safari is no fourth root: `SystemPorts.swift` (`FileSystemAppCatalog`);
- a read that was not `complete` drops nothing, and a read never writes: `Sources/Modules/Launchpad/Engine/Logic/LaunchpadReconcile.swift`, `LaunchpadEngine.swift`;
- every file read out of a bundle (`Info.plist`, `InfoPlist.strings` of the lproj `Bundle.preferredLocalizations` picks) goes through one reader that opens without blocking, follows no link at the last component, takes a regular file only and stops at `LaunchpadLimits.maxFileBytes`, so a pipe or a huge file planted in a bundle cannot hold the walk: `SystemPorts.swift` (`cappedRead`);
- in automatic mode a tile is at least `LaunchpadMetrics.tileMinimum` (132 pt) wide (or the icon asked for and its padding, if wider), a constant chosen from the widest unbreakable German word measured ("Datenträgerverwaltung", 120.5 pt at the subheadline font) and says its name in `.help`; the window's grid takes as many columns as that width fits (a manual grid of up to 10 columns goes under it, and `.help` carries the name): `Sources/Modules/Launchpad/UI/LaunchpadTiles.swift`, `Sources/Modules/Launchpad/UI/LaunchpadGeometry.swift`;
- the window measures nothing: its sizes come from the screen's size and the grid settings (once, and again only when those change: `regrid`), its pages are placed by offset, three at most exist as views, its icons are its own cache and go with it, and pass 3's page, in whose run the log showed the system switching the keyboard tap off and memory up 559 MB, is why: `LaunchpadGeometry.swift`, `LaunchpadScreen.swift`, `LaunchpadIcons.swift`, and `TheLaunchpadWindowMeasuresNothingTests`, an optional test run on request (`bash Scripts/test.sh --filter TheLaunchpadWindowMeasuresNothingTests`);
- the window's level is one below the Dock's, so the Dock stays drawn and clickable over it and the menu bar draws over its top strip (§ The Dock icon): `Sources/Modules/Launchpad/UI/LaunchpadWindow.swift`;
- the layout file is private, bounded, and a bad one is moved aside once before the first save: `LayoutStore.swift`, `Sources/Modules/Launchpad/Engine/Logic/LayoutCoding.swift`, `Sources/Modules/Launchpad/Engine/Logic/LaunchpadLimits.swift`.

## The catalog and the layout

`AppCatalogPort.read()` is pull-only; a change in the installed set is seen on the next read, and `observeChanges` tells the model when to ask (`CatalogChange.concerns` in `Sources/Modules/Launchpad/Engine/Logic/CatalogChange.swift` keeps a path that ends at an `.app` or at the `Info.plist` inside its `Contents`, and a path with no `.app` component unless its last component is hidden). An absent or empty root reads as empty and complete; a root that exists but will not open, or a walk stopped at the ceiling on apps, makes `CatalogReading.complete` false. The layout is saved only on a person's edit (`LaunchpadEngine.apply`), through one lock over read, reconcile, edit and save; only the latest catalog read is kept (an edit reconciles against it; the layout is read afresh each time) and the calls block on disk, so a model hops with `offTheCooperativePool`.

**Drops are edits by anchor.** An edit names where an item goes by the id of the item beside it, never by an index, because the window draws a subset of `layout.items` (`LaunchpadEdit`, `LaunchpadLayout.edit(dropping:source:destination:folderName:)` in `Sources/Modules/Launchpad/Engine/Logic/LaunchpadLayout.swift`; a folder never nests; a drop that changes nothing is nil). **A page break is an item**, `.pageBreak`, stored as `{"pageBreak": true}` in the same list (`LayoutCoding.swift`): it stays where it is when its neighbour is moved away, `normalized()` keeps one only between two items and at most `LaunchpadLimits.maxPages - 1` (199) of them, the later dropped, the file's version stays 1 and a file without breaks reads as it did. A catalog app carries its raw `LSApplicationCategoryType` (`CatalogApp.category`). **Folder names** are Helm's own words, copied from two tables of macOS and never read from them at run time (private files in a layout nobody promised): the iPhone's own folder-naming table, `FolderNaming.loctable` in `/System/Library/PrivateFrameworks/FrontBoard.framework/Versions/A/Resources` (`plutil -convert json -o - <it>`; tables `en`, `de`, `es`, `fr`, `ja`, `pt_BR`, `ru`, `zh_CN`), wherever it has the category; and for the six it lacks (Developer Tools, Graphics & Design, Video, Food & Drink, Magazines & Newspapers, Shopping) the descriptions of the `public.app-category.*` types in `/System/Library/CoreServices/CoreTypes.bundle/Contents/Resources/InfoPlist.loctable` (keys such as `Graphics n Design`). `LaunchpadCategoryName.swift` maps the 28 `public.app-category.*` ids that table lists, bar the games subtypes, to catalog words (`categoryBusiness` … `categoryWeather`; every `*-games` subtype is Games; the target's category, else the dropped app's, else `categoryOther`, "Others", which is plural and is Helm's own: Autopilot's "Other" is one file kind). Utilities and Video are the kit's words (`HelmWord.utilities`, `HelmWord.video`) since the host and Autopilot draw them too (§ Words two parts draw in `Architecture/Localization.md`). One exception to the first source: English "Health" is Homebrew's, so Healthcare & Fitness keeps CoreTypes' English (`OneEntryPerKeyTests`).

A hidden app leaves its folder. The module is not a `BackgroundScanning` module: it is read on demand with the person present, and has no report. The layout is not a sealed setting: it reorders and hides and names no path.

## The default arrangement

What a person sees with no arrangement of their own: `LaunchpadLayout.defaultArrangement(for:utilitiesFolderName:)` in `Sources/Modules/Launchpad/Engine/Logic/LaunchpadDefaultArrangement.swift`. Apple's apps stand in the Dock's order, then one folder of the system utilities, then a page break, then every other app in catalog (A–Z) order. It is used in two places only, both in `LaunchpadEngine`: a read or an edit with **no layout file** (`LayoutRead.absent`; the first edit saves what the person was shown, hidden apps aside), and `.resetArrangement`, which keeps `hidden` and takes the default's items. A stored layout is never rearranged by it, and an unreadable file still shows the catalog's order, as its warning says. New apps installed later go to the end, as `reconciled` always puts them.

Apps are told by bundle id, never by name; an id on the list that is not installed is skipped, and an app on no list falls into the A–Z block. The two lists are literals copied at build time and never read at run time: the Apple order from `persistent-apps` of the Dock's own default property list, in `/System/Library/CoreServices/Dock.app/Contents/Resources` (`plutil -p`; Keynote, Numbers and Pages are the `/Applications` ones), then the `/System/Applications` apps the Dock leaves out in the old Launchpad's order, `Apps` last; the utilities from the `CFBundleIdentifier` of every app in `/System/Applications/Utilities` plus Automator, Font Book, Image Capture and Time Machine. A utility is also any app whose path lies under `/System/Applications/Utilities/`, so one a later macOS adds lands in the folder. A folder of fewer than two members dissolves (`normalized()`). The folder has one fixed literal id, so an open folder survives the default being built again on each read. The folder's name is the kit word `HelmWord.utilities`, passed in as a closure by the descriptor (`LaunchpadEngine.init(utilitiesFolderName:)`), asked each time a default is built, so a language change shows; the engine holds no strings.

## How Launchpad's model reaches its engine

`LaunchpadViewModel` (`Sources/Modules/Launchpad/UI/LaunchpadViewModel.swift`) is built with the engine by the descriptor's `makeModule` and held by the host. It reaches the engine only through its `LaunchpadWork` port, which `LaunchpadEngine` conforms to: `read`, `hide`, `unhide`, `resetArrangement`, `launch`, `observeChanges`. Every blocking call hops off the main actor with `offTheCooperativePool`, and its answer is dropped when a newer request exists or the model was stopped: a snapshot by a newer read, a notice by a newer edit or launch (`LaunchpadViewModel.acts`). A launch's notice names the app on the tile that was pressed, taken before the launch.

A launch is resolved in the engine, not the model: `launch(id)` reads the catalog afresh, finds the id, asks the bundle at that fresh path for its id and only then hands the URL to `AppLauncherPort` (`Sources/Modules/Launchpad/Engine/Logic/LaunchResolution.swift`). A path never comes from the layout file or from the page's last snapshot. The answer is a `LaunchOutcome` (launched, gone, unreadable, failed); the model turns the last three into a notice. `SystemAppLauncher` (`Sources/Modules/Launchpad/Engine/SystemPorts.swift`) is the only code that opens an app, and in a test process it answers false and calls nothing (`TheSuiteDoesNotLaunchAppsTests`).

The model starts nothing in `init`. The settings page's `.task` and the window each call `whileShown()`, which subscribes to the catalog watch before its first read, so no change falls between the two; the token it gets is local to that task, so leaving cancels the task and stops the watch. Each caller is a watcher of its own: the snapshot and the notice are dropped when the last one leaves, and an answer that lands while nobody watches is refused, so a closed window holds no list of apps. Events are buffered to one, so a burst is one more read. On the person's switch and on quit the host calls the descriptor's `stop(_:)`, after which the model reaches no work.

## The window

The model is the one door: `showLaunchpad()` and `toggleLaunchpad()` (the shortcut's press) open the window or bring the open one forward, `closeLaunchpad()` and `stop()` close it; `present`, set by the descriptor, builds it, and a model without it (a test) opens nothing (`LaunchpadWindowHandle` is the seam). The shortcut is the descriptor's `LaunchpadHotkey` slot, with no default: it holds nothing until the person records one, and the host registers it only while the module is live.

`LaunchpadWindow` (`Sources/Modules/Launchpad/UI/LaunchpadWindow.swift`) is a borderless non-activating panel over the screen the pointer is on, not a `HostWindow`: Helm stays an accessory, with no Dock icon and no Space pulled. It is built when asked for, with its own `LaunchpadScreenState` (geometry, search, page, the arrow keys' choice, the open folder) and its own icons, runs the model's `whileShown()` while open, and releases all of it when it closes. It closes on Esc (an open folder first, then the search), a click on the empty background, an app that opened (a failed launch leaves it open with the notice), the panel losing key, another app coming forward, the Space or the screens changing, the model stopping and the shortcut's second press. Opening and closing each write one `module.launchpad.*` memory line. It opens by the panel's alpha fading up (`windowZoomDuration`, along `interfaceCurve`) while the content settles from `LaunchpadMetrics.zoomFrom` to its size; it closes by the model forgetting it at once and the picture fading out over `interfaceDuration` with the keys swallowed (`isClosing`) and the mouse ignored (`ignoresMouseEvents`, so a click goes through to what is behind), while the content zooms back on `windowZoom`, which the content's `.animation(_, value: shown)` owns, no matter what transaction sets `shown`; then `finish()` takes the panel down; a window opened over a fading one cuts it first (`lingering`). Reduce Motion cuts both and turns the zoom, the icon's pop and the glow off. A folder's card grows from its tile's slot (`LaunchpadGeometry.center(ofSlot:)`, computed, not measured) and folds back to it; the selected tile's wash (the arrow keys' choice, and the first search hit) carries a Metal glow (`LaunchpadGlow.metal`, compiled by SwiftPM into the target bundle's `default.metallib`, which the build needs the Xcode MetalToolchain component for; a failed compile is one log line and the plain wash). Tiles sit in left-aligned slots, so a short last row keeps its columns.

What is drawn follows `snapshot` and the search: busy (no answer yet), empty (no app), no match, or the pages, with a notice banner above the dots. Pages are an offset and a number. A trackpad swipe with fingers on it drags the page and settles it on release: `LaunchpadSwipe` (pure) turns each event into a drag or a release, the offset is a rubber band past the first and last page, a release turns by half a page or by a flick (300 pt/s from 40 pt), and a touch that begins while the last release settles is ignored; the 120 Hz of the drag publishes only `LaunchpadPageDrag.offset`, read by `PageDragOffset` alone, never the state; `settle` changes the page and zeroes the offset in one `withAnimation(HelmMotion.pageSettle(velocity:distance:))`. The wheel and a device with no phases turn one page (`LaunchpadScrollPager`), as do the arrows, the dots and the arrows' choice, all on `interface`; typing sends the page to the first at once and the tiles slide to their new slots, and the first snapshot is not animated. The arrows move a choice that Return opens (Left and Right stay the search field's while it holds text): an app launches, a folder opens a card over the dimmed page; hiding is the tile's context menu. A drag held when a folder opens or a search is typed is let go there, since no release will come. Under Reduce Motion a release settles at once and locks nothing.

### The grid settings

The page's Grid section (Automatic, Rows and Columns while Automatic is off, App icon size, Reset to defaults) is four plain keys in the module's store: `grid.automatic`, `grid.rows`, `grid.columns`, `grid.iconSize` (`LaunchpadGridSettings`; deployed stored data, the names never move). They are **not sealed**: sealing is for settings that steer unattended work (`Architecture/StoredSettings.md`), these choose a grid with the person present and a forged value only picks a number inside the ranges (rows 2 to 8, columns 3 to 10, icon 48 to 128 pt, whole points; not-a-number is the standard 80), as DisplayCorners' are not. The model reads them in `init`, in `showLaunchpad()` before the window is built and when the page appears, and writes through `setGrid` (clamped, refused when equal, only the changed keys, one log line); never per frame.

`LaunchpadGeometry.make(for:topSafe:settings:)` is pure. **Automatic** (the default; at icon 80 exactly the grid before the settings existed) counts columns by `max(tileMinimum, icon + 2 * tileSidePadding)` (at most 8) and rows by the icon's cell height (at most 6); **manual** takes the stored counts. The icon asked for is a ceiling: a grid that does not fit shrinks it, `fit(want:cellWidth:rowHeight:)`, to no less than `iconFloor` (24 pt). A label does not shrink (52 pt of chrome a row), so rows are capped at what the floor icon holds, `max(2, height / (24 + 52))`, which binds only on screens under about 770 pt tall (160 pt of top and dots room plus 8 rows of 76); the window's log line says "N rows asked, M fit". The folder card follows the grid (`columns - 1`, `rows - 1`) and has no setting. **Manual columns keep the grid as chosen and hide nothing**: with up to 10 columns a tile can be narrower than `tileMinimum`, so a long label is cut, and its `.help` names the app whole. The page's icon slider publishes the grid while it is dragged and writes the store once, when the drag ends (`commitGrid`).

A changed grid reaches an open window through the model's published `grid` and `LaunchpadScreenState.regrid`: it cancels a lift (a cell address is `page * capacity + slot` and means nothing in another capacity), makes the geometry again, tells the icon cache and cuts the same order into pages again, keeping the page by the choice or by the tile the shown page began with. **A changed grid re-pages and writes nothing** (`ARegridRepagesAndWritesNothingTests`); stored page breaks stay where they are. The panel closes when it loses key, so in use the new grid shows at the next open.

### Lifting a tile

A tile is lifted with raw mouse events, not SwiftUI's drag and drop (the source folder bans those words, `TheLaunchpadWindowMeasuresNothingTests`), and nothing is measured. `LaunchpadPanel.handle` converts a left press, drag and release to the window's top-left coordinates and gives them to `LaunchpadScreenState` (`pointerDown/Moved/Up`); it swallows a press only when the state says it began on a tile and a lift is allowed (`liftAllowed`: the grid shown, with no search text, no name being typed, no launch under way and the window shown; a press in an open folder's card is a lift too), so the background tap, the dots and the search field keep working, and while a press is held it swallows the wheel, the right button and every key but Esc. A press let go without moving is a click on that tile (`.click`: launch, or open the folder); the press wash is `state.pressedID`.

`LaunchpadLift` (pure struct, `Sources/Modules/Launchpad/UI/LaunchpadLift.swift`) is the machine: `feed(input, at:, surface:, time:)` returns **one** effect (`none`, `lift`, `moveGap`, `arm`, `turn`, `newPage`, `openFolder`, `closeFolder`, `release`, `cancel`, `click`) naming **cell addresses** (`page * capacity + slot`), and `wake` says when a tick would change something. `LaunchpadHit.at` finds what is under a point from `LaunchpadGeometry` and the per-page tile counts alone (a tile's core is the middle 60% of its width and the icon's height; the rest of the cell is its margin; the strip along either side is an edge). The numbers are `LaunchpadLiftTiming`: 5 pt to lift, 0.12 s in a margin before the gap moves, 0.30 s in the icon before a drop goes onto it, 40 pt edge, 0.6 s then every 0.9 s to turn the page, on the last page to make a new one. **The pointer over the gap itself changes nothing**, and the gap goes only by dwell, so a hundred moves inside a cell publish nothing.

The state holds a preview (the pages' segments with a `LaunchpadEntry.gap` of one stable identity where the carried tile was) and publishes only `lift` (the carried entry and the armed target; changes per slot or target) and `pages`; the pointer's place is `liftPoint`, a separate object read only by the overlay (the carried tile at 1.08, none under Reduce Motion, one `.offset`, no hit testing). One `@MainActor` task is armed for the sooner of `wake` and `stuckWake` and cancelled by `shutdown()` (window close); `stuckWake` is `LaunchpadLiftTiming.stuckCheck` (0.5 s) after the machine's last input while a press is engaged, so a mouse-up that never came is found by the tick's left-button read, and each tick moves it on (no zero-delay loop). The gap's id is `LaunchpadEntry.gapID`, a leading space, which no bundle id can spell, so an app named `gap` is not the gap. A release maps to a drop by anchors (`.beside` the neighbour in the gap's segment, `.onto`, `.newPage` when the gap is alone on the last page), `LaunchpadLayout.edit` makes the edit or nil, the page shows the result at once and `LaunchpadViewModel.place` writes it and answers the snapshot shown; a new folder opens when it lands. Nothing is written on Esc, an abort, the window closing, a left button not down on a tick, a search typed, or the carried app vanishing from a new snapshot (a snapshot that keeps it keeps the gap by its neighbour). Pages are the layout's items cut at `.pageBreak`, then by capacity (`LaunchpadPaging.pages`); a tile's index for the arrow keys is counted over the whole list (`pageStarts`).

**Folders in the lift.** A folder tile is a target twice: held 0.30 s on its icon it is armed (a release adds the app), held 0.70 s from arriving on it (`folderOpen`, counted from arrival like the 0.30 s, not from the drop being armed) its card opens (`LaunchpadLift.Effect.openFolder`, only when the carried tile is an app: folders never nest) and the same machine goes on against the card: `LaunchpadSurface.card` (`LaunchpadSurface.Card`, the rect of `LaunchpadGeometry.card`, shared with the drawing) makes `LaunchpadHit.at` answer with the card's tiles (index in the card, never a core, so nothing is armed), its empty cell, or `away` outside the card inflated 12 pt (`cardMargin`). The gap in the card is a `LaunchpadEntry.gap` in `cardEntries`, moved by the same margin dwell. The card closes (`closeFolder`) after the pointer has been **outside for 0.25 s (`leaveCard`) and only once it has been inside**: a card opens at the window's middle, not under the pointer that opened it, and without that rule it would close at once and open again. The lift goes on with its source (`LaunchpadDropSource.top`, or `.folder(id)` when lifted from inside a card, which a press on a tile of the open card does; a card that scrolls is left to its views). Release inside the card is `.intoFolder` (an add, or `moveInFolder` for a member), anywhere else the card closes first and it is a drop on the grid, `.beside` / `.onto` / `.newPage` with the source: a lift from a folder gives the grid a gap right after the folder's tile, whose tile meanwhile shows the folder without the carried app (the engine dissolves a two-app folder when the edit lands). Esc ends a lift and leaves the card open.

**The name.** The card's title is a `TextField` bound to `state.nameDraft`; `state.renaming` follows its focus (the view keeps both in step). While it is true `LaunchpadPanel.handle` asks `state.handleNameKey` first (after the marked-text and modifier guards): Return commits (trimmed, written through `LaunchpadViewModel.rename` only when it changed; blank reverts locally), Esc reverts and leaves the folder open, **every other key returns false** so the caret, the arrows and the typing are the field's. Closing the card commits a changed draft. Esc order: a lift, the name field, the folder, the search, the window. A folder just made opens with the field focused and its text selected (`beginRenaming(selectAll:)`, `TextSelection`).

## The Dock icon

Helm has no Dock icon, so Launchpad's is a second, tiny app nested in the bundle: `Helm.app/Contents/Helpers/Helm Launchpad.app` (Helm Dev: `Helm Dev Launchpad.app`), the target `HelmLaunchpadHelper` (`Sources/HelmLaunchpadHelper/main.swift`). The person drags its icon from the settings page to the Dock (the row also has "Show in Finder"; it is hidden when `AppBuild.launchpadHelperURL` is nil: `swift run`, a test host, a bundle packaged before the helper). A click starts the helper, which opens `helm-launchpad://toggle` at one explicit application, the Helm it sits in, without activating it, and quits. **Its shown name is the word for "Apps" in each language**, not its file name: `Resources/HelmLaunchpadHelper/<lang>.lproj/InfoPlist.strings` (`CFBundleDisplayName`, `CFBundleName`) with `LSHasLocalizedDisplayName`, copied into the bundle by `package-app.sh`. The words are the ones macOS's own Applications folder shows (`/System/Library/CoreServices/SystemFolderLocalizations/<lang>.lproj`; the system's tables for pt-BR and zh-Hans are `pt.lproj` and `zh_CN.lproj`): en and fr "Applications", de "Programme", es "Aplicaciones", ja "アプリケーション", zh-Hans "应用程序", pt-BR "Aplicativos"; ru is the owner's word, "Приложения" (macOS says "Программы"). Helm Dev shows "<word> Dev" (`rewrite-as-dev.sh`). The settings page names the helper by what Finder displays (`FileManager.displayName`) in the icon's and the button's VoiceOver labels. It is an accessory app that never shows a window and never activates, so the panel's "another app came forward" ender ignores it by bundle id (`LaunchpadWindowEnders`) and the click closes the window by toggling it.

**The link is input from outside the process**, so `LaunchpadLink.accepts` (`Sources/HelmRuntime/LaunchpadLink.swift`) compares the spelling `URL` gives back (normalised: `URL(string:)` drops invisible host characters such as U+200B, U+00AD and the byte-order mark, so a link that reads as the exact one after that is accepted, and the result is still only the toggle) with `<scheme>://toggle`: another scheme or host, a path (even `/`), a query, a fragment, a user or a port is refused, and `ModuleHost.openLaunchpadFromLink` logs one `link refused` line without the URL (one per throttle window, so a loop of bad links does not fill the log). Links closer than 0.5 s to the last accepted one are dropped (`LaunchpadLink.Throttle`), so a double click does not open and close the window. An accepted link presses the descriptor's own shortcut action, `hotkeyPressed`, so the Dock and the shortcut cannot disagree. With the module off the same link logs `link: module is off` and posts `.helmOpenSettings` for the Launchpad page, the way the status item does.

**One helper per channel.** The release helper's bundle id is `com.helm.app.launchpad` and its link scheme `helm-launchpad`; Helm Dev's are `com.helm.app.dev.launchpad` and `helm-dev-launchpad` (`AppBuild`). The helper's plist names its parent (`HelmParentBundleID`) and its link (`HelmLaunchpadURL`); the parent is the bundle three levels up when its id matches, else the app LaunchServices knows by that exact id. So a Helm Dev link never wakes the release. `Scripts/rewrite-as-dev.sh` rewrites all of it for Helm Dev, and a test reads the pair, and the shown names in every language, back from the staged and the rewritten bundle.

**Why Helm does not write the Dock.** A pin is the person's own, put there by dragging the icon (or by Keep in Dock), so nothing writes `com.apple.dock`, nothing restarts the Dock and nothing is left behind to remove. The cost is a stale pin when Helm moves: the Dock keeps the old path and the person drags the icon again; the page says so.

**The panel sits just below the Dock.** The window's level is `CGWindowLevelForKey(.dockWindow) - 1` (`LaunchpadWindow.level`): above every ordinary window, under the Dock, so the Dock draws over the panel and the pinned icon stays clickable, as macOS's own Launchpad leaves it. The frame is still the whole screen, and the menu bar, which is above the Dock's level, draws over the top strip.

## The Launchpad settings page

The page id is the module id, `launchpad`. A grouped form: a button that opens the window, the Dock-icon row (below), the shortcut's row (a taken combination is said), the grid (§ The grid settings), the hidden apps with a Show button each, and "Reset arrangement", which asks first: the press sets `pendingReset` and only the dialog's destructive button resets, once, keeping what is hidden (`LaunchpadEdit.resetArrangement`, reconciled in the engine so every shown app is back in the default arrangement, § The default arrangement). A notice banner above, no button: an app that is no longer installed, one that could not be opened, an arrangement that was not saved; it has no timer, and a launch that succeeds, a hide or a show, and the next appearance clear it.

The Dock-icon row is there only when the helper exists (`LaunchpadViewModel.helperURL`): the helper's own icon (`HelmDraggableFileIcon`, the kit's, dragged out as a file URL), a title, one sentence and "Show in Finder" (`HelmWord.showInFinder`, `HelmReveal.inFinder`, reached through the model's `revealHelper` that the descriptor sets, as `present`). § The Dock icon.

A state of the page is shot with `bash Scripts/shoot.sh launchpad ... --name <state>-<light|dark>` as the Disk page's states are (§ The states of the Disk page in `Architecture/Disk.md`). The window is shot live in Helm Dev, and nothing on the Mac is launched or removed to reach a state.
